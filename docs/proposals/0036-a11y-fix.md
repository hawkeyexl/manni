# 0036: `manni a11y fix`: deterministic repairs to local HTML

- **Status:** Proposed
- **Serves:** Theo · T1, the person with a red check who wants the one
  mechanical thing done for him. Maya · M1, clearing a backlog on a static site.
  a11y still has no persona of its own ([0035](0035-a11y-domain.md)).
- **Depends on:** [0035](0035-a11y-domain.md), which ships `check` and the
  finding shape (`rule`, `target`, `summary`) a fixer reads.
  [0018](0018-write-support-shipped-for-all-three.md) and
  [0020](0020-element-metadata.md), which built the parse5-based,
  offset-preserving HTML write path in `src/meta/extractors/html-write.ts` and
  `element-write.ts` that this reuses
- **Relates to:** [0005](0005-command-parity.md), parity with `meta fill`
  (`--dry-run`, positional paths, the shared input flags).
  [0017](0017-fill-egress-and-bounds.md), because `fill` sends document content
  to a provider and `fix` sends nothing anywhere, a difference worth stating on
  the page
- **Touches:** `src/a11y/commands/fix.ts` (new), `src/a11y/cli.ts` (a second
  verb), `src/a11y/core/config.ts` (`fix.lang`), the a11y docs pages; reuses,
  without changing, meta's HTML write path
- **Verdict:** Build `manni a11y fix <paths...>` over local HTML files, for
  the short list of axe rules whose fix needs no human decision. Report every
  other finding as "needs a person, here is the element". Not in the pull
  request that ships `check`.

## Problem

`manni a11y check` runs against a URL. It sees the rendered DOM and never the
source that produced it. That source is the Markdown, the template, the React
tree, the theme the static site generator applied. Nothing at the URL level can
be edited, so a `--fix` on `check` would have nothing to write to. That is a
structural fact, not a scope cut, and it is why 0035 answered the `--fix`
question with "no" rather than "later".

What `check` does give, and what 0035 shipped, is axe's own remediation
statement per failing element. That is the rule, the selector, and the condition
that failed. It appears in the node lines of `pretty` output and in
`ViolationNode.summary` in JSON. That is the same contract `meta validate` gives
Theo before `fill`. The finding names the field and the line, and a second
command may or may not be able to act on it.

A fixer needs files. The question this proposal answers is which findings a
fixer over local HTML could act on deterministically. The second question is
whether that list is long enough to be worth a command.

## Decision

### Which rules are mechanically fixable

The honest split of axe's rule set, for a fixer that edits HTML without asking
anyone anything:

| Mechanically fixable (no human decision) | Needs content or a design decision (not fixable deterministically) |
|---|---|
| `html-has-lang` / `html-lang-valid` (value from `--lang` or `a11y.fix.lang`), `meta-viewport` (drop `user-scalable=no`, `maximum-scale` < 2), `tabindex` (positive → `0`), `aria-hidden-body` (drop the attribute), `duplicate-id-aria`/`duplicate-id` only when no reference exists, `scope-attr-valid`, `presentation-role-conflict` (drop the role) | `image-alt`, `button-name`, `link-name`, `label`, `frame-title`, `document-title`, `color-contrast`, `heading-order`, `landmark-*`, `region`, `page-has-heading-one`, `bypass` |

Roughly seven rules on the left against the bulk of real-world findings on the
right. Every rule on the right needs either content a person has to write or a
design decision. The content is alt text, a button label, a page title; the
design decision is a colour, a heading level, a landmark structure. The only way
to fill the right column without a person is inference, a model writing the alt
text. That is `fill`'s territory, is not deterministic, and under 0017 sends the
document off the machine. `fix` does not do that. It does the left column, and
for the right column it prints the element and says a person is needed.

That is still worth a command. `html-has-lang` is among the most common axe
findings on generated sites. `meta-viewport` with `user-scalable=no` is a
template default in several themes. Positive `tabindex` values accumulate in
hand-written HTML. Each is a one-attribute edit that nobody wants to make by
hand across two hundred files.

### The surface

```
manni a11y fix <paths...>
      --dry-run            print the edits, write nothing
      --lang <tag>         value for html[lang] when it is missing or invalid
      --ext <list>         extensions when expanding directories (default html,htm)
      --exclude <glob>     glob to exclude, repeatable
  -f, --format <format>    pretty | json | github          (pretty)
  -c, --config <path>      explicit config file
      --no-config          ignore any discovered config
```

Parity with `meta fill` where the two mean the same thing. That is positional
targets that are files, directories and globs, and `--dry-run` as the preview.
`--ext` is a `<list>` and `--exclude` repeatable, both under 0034's separator
rule. `-f` has the same three values `check` has, and `-c` and `--no-config`
match. Config lives under `a11y.fix`, with `lang` the only key at first.

Two things are open and left so on purpose. Whether `<paths...>` is required, as
written here, or optional with a config fallback (`a11y.fix.paths`) the way
every meta command's `[paths...]` is. 0005 argues for the fallback; the a11y
config key has `urls` and no notion of local paths yet, and inventing one for a
`Proposed` command is premature. And whether `fix` should also *run the check*
on the files it edits, so its report is the before-and-after. The alternative is
to leave verification to a second `check` against the served site. The second is
simpler and honest about what `fix` can see.

### Reuse

meta already parses HTML with parse5, locates elements, and writes attribute
edits back at byte offsets. Nothing else in the file moves. That is
`html-write.ts` and `element-write.ts`, built for `fill` under 0018 and 0020.
Every fix in the left column is an attribute add, change or drop on one element,
which is exactly the operation that path supports. `fix` imports it by relative
path (`../meta/extractors/…`), as the folding-in recipe says a tool imports the
metadata library, and changes nothing in it.

Finding the elements to fix does not need a browser. Every left-column rule
is decidable from static markup: `html[lang]` is present or not, a `tabindex`
is positive or not, an id is duplicated or not. `fix` therefore runs axe's
*rule logic* only where it can be reproduced statically, and does not launch
Playwright. That keeps `fix` runnable in a `postbuild` step on a machine with
no browser at all.

### What it prints

`pretty`: one line per file per edit, `<path>:<line>  <rule>  <what changed>`.
Under a heading "needs a person" it prints one line per right-column finding
with the selector and axe's summary. That is the same node line `check` prints.
`--dry-run` prints the same with a `would` prefix and writes nothing. `json`: an
array of `{ file, edits[], manual[] }`. `github`: a `::notice` per edit and a
`::warning` per manual finding, on the file and line. Exit `0` when every
finding was either fixed or reported as manual. Exit `1` when a fix could not be
applied (an unwritable file, an edit that would conflict), and `2` for
`A11yError`.

## Stress test

### 1. The files are built output, and the generator regenerates them

The common case for a docs site: `dist/` is produced by Astro, Docusaurus or
Hugo, and any edit to it is gone on the next build. Fixing `dist/` is then a
one-off that teaches nothing.

Two answers. First, `--dry-run` over `dist/` is still the useful product. It
turns a URL finding into a *file and line* finding in the output, which is one
step closer to the template than `check` can get. For a theme-level defect
(`user-scalable=no` in a layout) one line in `dist/` points straight at one line
in the theme. Second, hand-written HTML exists: legacy sites, exported help
systems, the `public/` folder of a generated site, email templates. For those
the edit is durable. The page for `fix` says which case the reader is in, and
leads with `--dry-run`, the way the T1 page leads with it for `fill`.

### 2. `lang` needs a value, and the tool cannot know it

`html-has-lang` is the most common left-column finding and the one whose fix is
not zero-decision: something has to choose `en`. The tool does not guess from
content, because language detection on a short page is unreliable. A wrong
`lang` is worse than none (screen readers switch pronunciation on it). So
`--lang` or `a11y.fix.lang` is required for that rule, and with neither set the
finding moves to the manual list with the message "set `--lang` or
`a11y.fix.lang`". A site with pages in several languages sets it per directory
in config. That is a second key (`a11y.fix.overrides`, mirroring meta's) and a
reason the surface is `Proposed` rather than `Accepted`.

### 3. Duplicate ids may be referenced by scripts and styles

Renaming one of two duplicate `id`s fixes the axe finding and breaks the
`getElementById` that found the first one, or the `#id` CSS selector that
styled both. That is why the table says `duplicate-id` is fixable *only when
no reference exists*: `fix` renames only when the file itself contains no
`href="#id"`, no `for="id"`, no `aria-*="id"`, no `<style>` or `<script>` text
containing the id. An external stylesheet or script can still reference it,
and the tool cannot see those. So the default for `duplicate-id` is manual,
with the rename offered under a flag (`--rename-duplicate-ids`) whose help text
says what it cannot check. Better a fix the user opted into than one they
discover in production.

### 4. Why not `--fix` on `check`, with paths mapped from URLs?

A `--root dist/` on `check` that maps `https://site/x/` to `dist/x/index.html`
would let one command find and fix. It was declined because the mapping is a
guess (trailing-slash policy, `index.html` vs `x.html`, base paths, i18n
prefixes), and a wrong guess edits the wrong file. Two commands with two
clear inputs, a URL and a path, are two things a reader can predict. The
shape follows `validate`/`fill` in meta, which are also two commands over the
same findings.

### 5. Is seven rules worth a verb?

The count of rules understates it. The left-column rules are the ones that
appear on every page of a site at once, because they come from the template.
They are `lang`, `viewport`, a body-level `aria-hidden`. A single finding in the
template is two hundred findings in `check`'s output. Clearing them is what lets
a team see the right-column findings that need their attention. A verb that
removes the noise so the signal shows is the same job `fill` does for the
metadata backlog.

## Consequences

- If accepted, `a11y` gains a second verb and the domain's reference page a
  second `## \`a11y fix\`` section under the drift check. `check` does not
  change.
- `src/meta/extractors/html-write.ts` and `element-write.ts` gain a second
  consumer and no changes. If the write path needs a new operation (a rename
  across references, say), that goes into meta's extractor with its own tests.
  The reason is that meta owns that file.
- `fix` sends nothing off the machine and launches no browser, and its page says
  both. The link to `fill`'s egress page sits next to that, so the contrast is
  visible.
- The open questions (paths fallback, per-directory `lang`, opt-in id renames)
  are answered in the plan that implements this, under 0034's rules. That means
  the full surface and a ladder from `manni a11y fix dist/ --dry-run` to the
  every-flag form, before code.
- The right column stays the right column. Nothing here proposes a model writing
  alt text under the a11y domain. If that is ever wanted, it is a `fill`-shaped
  proposal with 0017's egress analysis attached.
