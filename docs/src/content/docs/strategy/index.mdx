`manni strategy` is in beta. Its commands, config keys and output can change
in any release, without notice.
</Aside>

A docset's content strategy says whom it serves. manni strategy keeps that
strategy as **records**, and checks every page that names one against them.

A record is a page that declares one of three types. It is one record per
file, in any format manni meta reads.

- **An audience** declares `type: audience`. It is a group of readers.
- **A persona** declares `type: persona`, and names its audience in
  `audience:`.
- **A journey** declares `type: journey`, and names the personas it serves
  in `personas:`. A journey can serve more than one persona.

A record's `id` is its `id:`, or else its file name without the extension.
`list` and `get` print its `title` and `description`. This is the journey
this section serves, as this repository keeps it:

```markdown title="docs/content-strategy/journeys/s17.md"
---
type: journey
id: s17
title: Hold the pages to the strategy they were written for
description: The audiences, personas and journeys Sara's docs serve are records, and every page that names one is checked against them.
personas: [sara]
---
```

The prose below the frontmatter is the journey itself. No rule reads it.

A journey can also carry `lifecycle`, from the
[`manni:lifecycle:1.0.0`](/manni/meta/reference/schemas/manni-lifecycle/)
vocabulary. A `draft` journey is not live yet, and an `archived` one no
longer is. Neither is expected to have a page, so `check` skips both when it
looks for an unserved journey. A journey can land as a draft before its pages
exist.

Records also carry the fields
[`manni test tasks`](/manni/test/attempt-a-task/) reads, where a synthetic
user attempts a journey as one of its personas. No `strategy` rule reads them.

- A journey's `trigger`, `entry-point` and `success-criteria` tell the
  synthetic user what started the task, where to begin, and when it is done.
- A journey's `workspace` names the directory each run starts from.
- A journey's `evals:` are eval entries that say what done looks like.
  Journeys that declare `evals:` are the golden set, which a bare
  `manni test tasks` runs.
- A persona's `goals`, `pains` and `constraints` tell the synthetic user who
  it plays. Each constraint is judged after the run, as a warning.

`manni meta validate` checks a record's fields against the schemas a repo
applies through `meta.overrides`. This repository keeps one schema per record
type, for an
[audience](https://github.com/hawkeyexl/manni/blob/main/docs/content-strategy/schemas/audience.schema.json),
a
[persona](https://github.com/hawkeyexl/manni/blob/main/docs/content-strategy/schemas/persona.schema.json)
and a
[journey](https://github.com/hawkeyexl/manni/blob/main/docs/content-strategy/schemas/journey.schema.json).
Three overrides apply them. The journeys override also lists the lifecycle
vocabulary, so a value such as `lifecycle: drafty` fails `meta validate`:

```yaml title="manni.config.yaml"
meta:
  overrides:
    - files: "docs/content-strategy/audiences/*.md"
      schemas: [./docs/content-strategy/schemas/audience.schema.json]
    - files: "docs/content-strategy/personas/*.md"
      schemas: [./docs/content-strategy/schemas/persona.schema.json]
    - files: "docs/content-strategy/journeys/*.md"
      schemas:
        - ./docs/content-strategy/schemas/journey.schema.json
        - manni:lifecycle:1.0.0
```

## What a page names

A page says whom it serves in three fields of the
[`manni:audience:1.0.0`](/manni/meta/reference/schemas/manni-audience/)
vocabulary. Each value is a reference, and the check resolves it against the
records.

| Field | Names | Where it lives |
|---|---|---|
| `audiences:` | audience records | the page |
| `personas:` | persona records | the page or its `{page}.meta.yaml` sidecar |
| `journeys:` | journey records | the page or its `{page}.meta.yaml` sidecar |

A value in a sidecar counts as one in the page does. A finding about it sits
at the sidecar's line.

{/* cite field-gated-on-records */}
A field is checked only when the set holds a record of its type. A docset
that keeps persona records and no audience records keeps a free-form
`audiences:`, and no rule reads it. So the records can arrive one type at a
time.

## Set it up

The records and the pages come from the family's
[collections](/manni/meta/reference/configuration/#collections). Give the
records a collection of their own. This is this repository's config, cut to
the lines the domain reads:

```yaml title="manni.config.yaml"
collections:
  - name: site
    paths:
      - "docs/src/content/docs/**/*.{md,mdx}"
    externalMetadata:
      - file: "{page}.meta.yaml"
  - name: strategy
    paths:
      - "docs/content-strategy/{audiences,personas,journeys}/*.md"
```

The overrides above then check each record's fields.

The `strategy:` section is optional, because every key has a default. The
[configuration reference](/manni/strategy/reference/cli/#configuration)
lists the keys. This repository raises one rule, so a journey cannot land
without a page that serves it, unless it lands as a draft:

```yaml title="manni.config.yaml"
strategy:
  severity:
    unserved-journey: error
```

## Three commands

| Command | Does |
|---|---|
| `manni strategy list [paths...]` | Prints the records as a tree, with how many pages name each one. |
| `manni strategy get <id> [paths...]` | Shows one record, its parents, the records under it, and the pages that name it. |
| `manni strategy check [paths...]` | Checks every reference against the records, and the records against each other. |

Run with no paths, each command reads every collection. Here they run over
a set of one audience, one persona and two journeys, which two pages name.
`list` prints the tree:

```console
$ manni strategy list
record            pages  title
docs-engineers        2  Docs-as-code teams
  maya                2  Maya, Documentation Engineer
    m1                2  Stand up metadata validation for my repo
    m2                1  Tighten the standard without breaking the build
1 audience, 1 persona, 2 journeys
```

`get` matches the id in any case. Its `pages` row answers which pages serve
the record:

```console
$ manni strategy get maya
Maya, Documentation Engineer                  strategy/personas/maya.md:1
  type          persona
  id            maya
  description   Owns a docs-as-code repo and wants its frontmatter correct.
  audience      docs-engineers  Docs-as-code teams
  journeys      m1  Stand up metadata validation for my repo
                m2  Tighten the standard without breaking the build
  pages         docs/ci.md
                docs/guide.md
```

Every reference resolves, so `check` prints one line and exits `0`:

```console
$ manni strategy check
✓ 4 records, 10 references, no findings
```

In another set, a guide names a journey that has no record, and a journey
whose persona the page leaves out:

```markdown title="docs/guide.md"
---
title: Guide
audiences: [docs-engineers]
personas: [devin]
journeys: [m1, m9]
---
```

`check` reports both at the line of the value that caused them:

```console
$ manni strategy check
docs/guide.md:5
  warning manni:strategy/missing-parent       personas: does not name "maya", the persona of journey "m1".
                                              Add it, or drop "m1" from journeys:.
                                              manni:strategy missing-parent: A page names a journey but none of its personas in personas:, or a persona but not its audience in audiences:.
                                              Guide: https://hawkeyexl.github.io/manni/strategy/reference/rules/#missing-parent
  error   manni:strategy/undefined-reference  journeys: "m9" names no journey.
                                              Did you mean "m1"?
                                              Correct the value, or add a record with type: journey and id: m9.
                                              manni:strategy undefined-reference: A page's audiences:, personas: or journeys:, or a record's audience: or personas:, names no record of that type.
                                              Guide: https://hawkeyexl.github.io/manni/strategy/reference/rules/#undefined-reference
```

{/* cite check-exits-one-on-error */}
That set breaks every rule once, so the run goes on to five findings about
the records. It ends `3 errors, 3 warnings, 1 notice in 7 records`, and it
exits `1` because of the errors. Warnings and notices never fail a run.

## Map a journey's steps to its pages

A journey's `steps:` lists its stages in order, each with the page that
carries it. A step's `doc` is a repo path, or a site route that
`graph.routes` maps to a file. A page still to be written says
`exists: false`:

```markdown title="strategy/journeys/m1.md"
---
type: journey
id: m1
title: Stand up metadata validation for my repo
personas: [maya]
steps:
  - stage: Read the guide
    doc: docs/guide.md
  - stage: Add the CI step
    doc: /site/ci/
  - stage: Look up a flag
    doc: docs/reference.md
  - stage: Work through the tutorial
    doc: /site/tutorial/
    exists: false
---
```

`get` then shows the path in order, with each step's state and page:

```console
$ manni strategy get m1
Stand up metadata validation for my repo      strategy/journeys/m1.md:1
  type          journey
  id            m1
  personas      maya  Maya, Documentation Engineer
  steps         2 of 4 served
                1  served     Read the guide
                              docs/guide.md
                2  served     Add the CI step
                              docs/ci/index.md
                3  unclaimed  Look up a flag
                              docs/reference.md
                4  unwritten  Work through the tutorial
                              /site/tutorial/
  pages         docs/ci/index.md
                docs/guide.md
```

The reference page carries stage 3, but its own `journeys:` leaves out `m1`.
`check` names that as a `missing-journey` warning on the step's `doc:` line.
It names the unwritten tutorial as an `unwritten-step` notice. A `doc` that
names no page at all is a `broken-step` error. `list` adds a `steps` column
with each journey's served steps over its steps. The
[steps section](/manni/strategy/reference/rules/#steps) of the rules
reference has every state.

## Measure it against readers

The check says the pages agree with the records. It cannot say whether
readers take the journeys.
[Measure the strategy against reader traffic](/manni/strategy/traffic/)
joins a page-views export to the records, for traffic per journey and per
persona.

## Every finding has a rule

Each finding names its rule, and its `Guide:` line links to that rule's
section of the [rules reference](/manni/strategy/reference/rules/). That page
gives each of the ten rules its default severity, its exact message, and the
edit that clears it. It also has the full run of the set above.

## What manni strategy checks, and what it doesn't

<CardGrid>
  <Card title="It checks" icon="approve-check">
    That every `audiences:`, `personas:` and `journeys:` value names a record
    of its type. That a record's `audience:` or `personas:` names one too.
    That no two records share an id, ignoring case. That a page naming a
    journey also names one of its personas, and a persona its audience. That
    some page names every journey that is not a draft or archived. That each
    journey step names a page, and that the page names the journey.
  </Card>
  <Card title="It doesn't" icon="close">
    Read the prose of a record or a page. It doesn't require a page to carry
    `journeys:` either. That is a question of presence, so it belongs to
    manni meta, as a schema override with `required: [journeys]`.
  </Card>
</CardGrid>

## With the other domains

The domain is in play once a collection holds a record. `manni status` then
shows the strategy row, with a count of each type. `manni check` runs
`manni strategy check` beside the other domains' checks.
[Gate every check](/manni/family/check/) covers the family verbs, and
the [family CLI reference](/manni/family/reference/cli/) has the in-play
rule for each domain.
