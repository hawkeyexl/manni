A glossary kept in one construct is not stuck there. `manni term` reads a
term set from pages, from body constructs in six formats, and from manifests.
`manni term write` renders the same set into another shape, or into an
interchange format a translation system imports. This page moves a DocBook
glossary to one Markdown page per term and back. Then it hands the set off as
TBX and CSV, and reads the translated termbase back.

Every transcript below is real output from the built tool.

## What each construct holds

A construct is read for what it can say, and no further. A definition list
has nowhere to put a scope note, so no scope note is read from one.

| Construct | Needs `type: term-set` | Reads |
|---|---|---|
| Page metadata, `type: term`, in any format | n/a | every field |
| YAML or JSON manifest under [`term.manifests`](/manni/term/reference/configuration/#a-manifest) | n/a | every field |
| TBX v2 or v3 entry, in a `.tbx` file | no | every field except `abstract`, `broader`, `narrower`, `related-terms`, `see` and `scope-note`, a term per language |
| DITA `<glossentry>` topic | no | `label`, `definition`, `alt-labels`, `scope-note`, `id` |
| DITA `<glossgroup>` | no | the same, per child `<glossentry>` |
| DocBook `<glossary>` | no | `label`, `definition`, `alt-labels`, `see`, `related-terms`, `id` |
| HTML `<dl>` | yes | `label`, `definition`, `alt-labels`, `id` |
| HTML `<dfn>` | yes | `label`, `alt-labels`, `id` |
| Markdown or MDX definition list | yes | `label`, `definition`, `alt-labels` |
| AsciiDoc `[glossary]` list | no | `label`, `definition`, `alt-labels` |
| reStructuredText `.. glossary::` | no | `label`, `definition`, `alt-labels` |

{/* cite several-terms-docbook */}
{/* cite several-terms-html-dl */}
{/* cite several-terms-body-lists */}
Where a construct allows several terms against one definition, the first is
the label and the rest are alt-labels. That covers several `<dt>` before one
`<dd>`, several terms in one `.. glossary::` entry, and a DocBook `<glossterm>`
beside an `<acronym>`.

DITA's element names are the only ones that differ from the record's:

| DITA | Field |
|---|---|
| `<glossterm>` | `label` |
| `<glossdef>` | `definition` |
| `<glossAlt><glossSynonym>` | `alt-labels` |
| `<glossAlt><glossAcronym>` | `alt-labels` |
| `<glossBody><glossUsage>` | `scope-note` |
| topic `@id` | `id` |

{/* cite formats-lists-read-write */}
`manni term formats` prints what the build reads and writes, per format. The
[CLI reference](/manni/term/reference/cli/#term-formats) shows its output.

## Move a DocBook glossary to pages

The starting point is one DocBook file holding three entries. `varifocal` is a
redirect to `progressive-lens`:

```xml title="docs/glossary.xml"
<?xml version="1.0" encoding="UTF-8"?>
<article xmlns="http://docbook.org/ns/docbook" version="5.0">
  <title>Optics</title>
  <glossary>
    <title>Glossary</title>
    <glossentry xml:id="bifocal">
      <glossterm>bifocal</glossterm>
      <glossdef>
        <para>Lenses with two distinct optical powers, divided by a visible line.</para>
      </glossdef>
    </glossentry>
    <glossentry xml:id="progressive-lens">
      <glossterm>progressive lens</glossterm>
      <acronym>PAL</acronym>
      <glossdef>
        <para>Corrective lenses whose optical power increases continuously from the top of the lens to the bottom.</para>
        <glossseealso otherterm="bifocal"/>
      </glossdef>
    </glossentry>
    <glossentry xml:id="varifocal">
      <glossterm>varifocal</glossterm>
      <glosssee otherterm="progressive-lens"/>
    </glossentry>
  </glossary>
</article>
```

<Steps>

1. **See what is read.**

   ```sh
   manni term list docs/glossary.xml
   ```

   ```
   bifocal            bifocal
   progressive-lens   progressive lens   PAL
   varifocal          varifocal
   3 terms
   ```

2. **Render one page per term.** The trailing `/` makes `-o` a directory, so
   each entry gets a file named after its id:

   ```sh
   manni term write docs/glossary.xml -f markdown -o docs/terms/
   ```

   ```
   Wrote 3 terms to docs/terms/, one file each
   ```

   ```markdown title="docs/terms/progressive-lens.md"
   ---
   title: progressive lens
   type: term
   id: progressive-lens
   label: progressive lens
   definition: Corrective lenses whose optical power increases continuously from the top of the lens to the bottom.
   alt-labels:
     - PAL
   related-terms:
     - bifocal
   ---
   ```

   A page holds every field, so nothing was dropped. `<glossseealso>` became
   `related-terms`, and `<glosssee>` became `see` on `varifocal`.

3. **Grow the pages.** A page can now carry what DocBook could not. This one
   gains a language, an abstract, a hidden-label and a scope note:

   ```markdown title="docs/terms/progressive-lens.md"
   ---
   title: progressive lens
   type: term
   id: progressive-lens
   language: en
   label: progressive lens
   definition: Corrective lenses whose optical power increases continuously from the top of the lens to the bottom.
   abstract: Lenses that correct presbyopia without a visible line.
   alt-labels:
     - PAL
   hidden-labels:
     - no-line bifocal
   related-terms:
     - bifocal
   scope-note: Spectacle lenses only. Contact lenses are out of scope.
   ---
   ```

</Steps>

## Render back into one file

{/* cite file-shape-one-file */}
{/* cite dropped-report-line */}
A path without a trailing `/`, naming no existing directory, gets every entry
in one file. The format's list construct cannot hold every field, and the
report says what was dropped:

```sh
manni term write docs/terms/ -f docbook -o build/glossary.xml
```

```
Wrote 3 terms to build/glossary.xml
  dropped from a DocBook glossary: abstract on 1 term, hidden-labels on 1, scope-note on 1
```

```xml title="build/glossary.xml"
<?xml version="1.0" encoding="UTF-8"?>
<glossary xmlns="http://docbook.org/ns/docbook" version="5.0">
  <title>Glossary</title>
  <glossentry xml:id="bifocal">
    <glossterm>bifocal</glossterm>
    <glossdef>
      <para>Lenses with two distinct optical powers, divided by a visible line.</para>
    </glossdef>
  </glossentry>
  <glossentry xml:id="progressive-lens">
    <glossterm>progressive lens</glossterm>
    <acronym>PAL</acronym>
    <glossdef>
      <para>Corrective lenses whose optical power increases continuously from the top of the lens to the bottom.</para>
      <glossseealso>bifocal</glossseealso>
    </glossdef>
  </glossentry>
  <glossentry xml:id="varifocal">
    <glossterm>varifocal</glossterm>
    <glosssee>progressive-lens</glosssee>
  </glossentry>
</glossary>
```

{/* cite deflist-holds-label-definition-alts */}
A Markdown definition list holds less again. It keeps the label, the
definition and the alt-labels:

```sh
manni term write docs/terms/ -f markdown -o glossary.md
```

```
Wrote 2 terms to glossary.md
  dropped from a definition list: abstract on 1 term, hidden-labels on 1, related-terms on 1, scope-note on 1
  skipped 1 term a definition list cannot read without a definition: varifocal
```

```markdown title="glossary.md"
---
type: term-set
---

bifocal
:   Lenses with two distinct optical powers, divided by a visible line.

progressive lens
PAL
:   Corrective lenses whose optical power increases continuously from the top of the lens to the bottom.
```

<Aside type="caution" title="A redirect needs a target that holds see">
A definition list has no place for `see`, and an entry with no definition
reads back as nothing. So `varifocal` is left out, and the run names it. The
same goes for an AsciiDoc `[glossary]` list, a `.. glossary::` and an HTML
`<dl>`. DITA, TBX and SKOS drop `see` too. Keep redirects in pages, a
manifest, DocBook, CSV or JSON.
</Aside>

{/* cite dry-run-files-then-notes */}
{/* cite dry-run-writes-nothing */}
`--dry-run` prints the files a render would create or change, then the same
dropped and skipped lines a write prints, and writes nothing:

```console
$ manni term write docs/terms/ -f markdown -o glossary.md --dry-run
glossary.md would be created
  dropped from a definition list: abstract on 1 term, hidden-labels on 1, related-terms on 1, scope-note on 1
  skipped 1 term a definition list cannot read without a definition: varifocal
```

{/* cite check-prints-only-files */}
{/* cite check-exit-1-when-differs */}
{/* cite check-clean-up-to-date */}
`--check` prints only the files, and exits `1` when one differs. When none
does, it prints that the target is up to date.

## What each render holds

| `-f` | `-o` a directory | `-o` a file | Holds |
|---|---|---|---|
| `markdown`, `mdx`, `asciidoc`, `rst` | one term page per entry | a definition list, a `[glossary]` list, or a `.. glossary::` | a page holds every field. A list holds `label`, `definition` and `alt-labels` |
| `html` | one term page per entry, fields in `<meta>` | a `<dl>` | a page holds every field. A `<dl>` holds `label`, `definition`, `alt-labels` and `id` |
| `dita` | one `<glossentry>` topic per entry | a `<glossgroup>` | `label`, `definition`, `alt-labels`, `scope-note`, `id` |
| `docbook` | refused | a `<glossary>` | `label`, `definition`, `alt-labels`, `see`, `related-terms`, `id` |
| `tbx` | refused | TBX v2 | every field except `abstract`, `broader`, `narrower`, `related-terms`, `see` and `scope-note` |
| `tbx3` | refused | TBX v3 | the same as `tbx` |
| `skos` | refused | a SKOS concept scheme in JSON-LD | the ten SKOS fields except `abstract` and `see` |
| `csv` | refused | one row per id | the ten SKOS fields, a column set per language |
| `json` | refused | `{ "terms": [...] }` | every field |
| `vale` | the `Terms` style | n/a | see [the generated style](/manni/term/set-up/#the-generated-style) |

{/* cite directory-target-refused */}
A directory target for a format that writes one file stops with exit `2`:

```
manni: -f tbx writes one file, not a directory. Pass -o <file>.
```

## What a round trip does not keep

A render writes the record, and a read of the result builds a record again.
Three things do not survive that trip.

### A line break inside a paragraph

This definition has a line break inside its first paragraph, and a paragraph
break before its second:

```console
$ manni term get "progressive lens" docs/terms -f json
{
  "id": "progressive-lens",
  "label": "progressive lens",
  "definition": "Corrective lenses whose power increases\nfrom the top of the lens to the bottom.\n\nThey correct presbyopia without a visible line."
}
```

{/* cite deflist-writes-line-break */}
{/* cite deflist-reads-break-as-space */}
A definition list writes the break, and reads it back as a space:

```console
$ manni term write docs/terms -f markdown -o build/glossary.md
Wrote 1 term to build/glossary.md
$ manni term get "progressive lens" build/glossary.md -f json
{
  "id": "progressive-lens",
  "label": "progressive lens",
  "definition": "Corrective lenses whose power increases from the top of the lens to the bottom.\n\nThey correct presbyopia without a visible line."
}
```

{/* cite list-constructs-read-break-as-space */}
{/* cite markup-lists-one-line-per-paragraph */}
{/* cite docbook-one-line-per-paragraph */}
The paragraph break survives. The same happens in every list construct. A
Markdown or MDX definition list, an AsciiDoc `[glossary]` list and a
`.. glossary::` read the break back as a space. An HTML `<dl>`, a DITA
`<glossentry>` or `<glossgroup>`, and a DocBook `<glossary>` write each
paragraph on one line:

```xml title="build/glossary.xml"
<glossdef>
  <para>Corrective lenses whose power increases from the top of the lens to the bottom.</para>
  <para>They correct presbyopia without a visible line.</para>
</glossdef>
```

{/* cite tbx-definition-as-is */}
{/* cite csv-definition-as-is */}
A term page, in Markdown or HTML, keeps the break. So do TBX, SKOS, CSV and
JSON, which write the definition as it is. Where a break matters, keep the
definition in pages, or make it a paragraph break.

### An id in a construct with no identifier

{/* cite list-entry-id-is-label-slug */}
A Markdown or MDX definition list, an AsciiDoc `[glossary]` list and a
`.. glossary::` have nowhere to store an id. An entry read back from one gets
the slug of its label:

```console
$ manni term list docs/terms
pal-lens   progressive lens
1 term
$ manni term write docs/terms -f markdown -o build/glossary.md
Wrote 1 term to build/glossary.md
$ manni term list build/glossary.md
progressive-lens   progressive lens
1 term
```

{/* cite id-not-a-dropped-field */}
{/* cite page-file-named-after-id-changes */}
The run does not list `id` among the dropped fields. A page rendered from that
list is `build/terms/progressive-lens.md`, with `id: progressive-lens`. So an
id that is not the slug of its label changes, and so does the file named
after it.

{/* cite page-keeps-id */}
{/* cite html-dl-reads-dt-id */}
{/* cite html-dl-writes-dt-id */}
{/* cite dita-keeps-topic-id */}
{/* cite docbook-keeps-xml-id */}
Pages and manifests keep the id. So do an HTML `<dl>`, through `<dt id>`, a
DITA topic `id`, and a DocBook `xml:id`:

```console
$ manni term write docs/terms -f html -o build/glossary.html
Wrote 1 term to build/glossary.html
$ manni term list build/glossary.html
pal-lens   progressive lens
1 term
```

### Markup the record has no field for

{/* cite render-writes-only-record-fields-docbook */}
A render writes only the record's fields. An attribute or element outside
them is not carried into the output, even when the source and the target are
the same format. This DocBook entry carries a `role`:

```xml title="docs/glossary.xml"
<glossentry xml:id="progressive-lens" role="clinical">
  <glossterm>progressive lens</glossterm>
  <glossdef>
    <para>Corrective lenses whose power increases from the top of the lens to the bottom.</para>
  </glossdef>
</glossentry>
```

Rendered to DocBook, the `role` is gone:

```console
$ manni term write docs/glossary.xml -f docbook -o build/glossary.xml
Wrote 1 term to build/glossary.xml
$ cat build/glossary.xml
<?xml version="1.0" encoding="UTF-8"?>
<glossary xmlns="http://docbook.org/ns/docbook" version="5.0">
  <title>Glossary</title>
  <glossentry xml:id="progressive-lens">
    <glossterm>progressive lens</glossterm>
    <glossdef>
      <para>Corrective lenses whose power increases from the top of the lens to the bottom.</para>
    </glossdef>
  </glossentry>
</glossary>
```

{/* cite unknown-markup-not-dropped-field */}
{/* cite dita-outputclass-not-written */}
{/* cite docbook-bare-glossary-titled-glossary */}
The run reports no dropped field, because `role` is not a field. The same
goes for a DITA `outputclass`. The document around the glossary is not carried
either. The source's `<article>` and its `Optics` title became a bare
`<glossary>` titled `Glossary`. A render is a new file, so keep the source
where that markup lives.

TBX is the exception. Its reader keeps an element no field names in
`tbx-elements`, and inline markup in `tbx-markup`, so a TBX render puts them
back. [Read the termbase back](#read-the-termbase-back) shows what it keeps.

## Hand the set to a translation system

<Steps>

1. **Write TBX.** TBX is the termbase exchange format translation systems
   import. `-f tbx` writes TBX v2, and `-f tbx3` writes TBX v3. The kind of
   label becomes each designation's status:

   ```sh
   manni term write docs/terms/ -f tbx -o build/terms.tbx
   ```

   ```
   Wrote 3 terms to build/terms.tbx
     dropped from tbx: abstract on 1 term, related-terms on 1, see on 1, scope-note on 1
   ```

   ```xml title="build/terms.tbx"
   <?xml version="1.0" encoding="UTF-8"?>
   <martif type="TBX" xml:lang="en">
     ...
         <termEntry id="progressive-lens">
           <langSet xml:lang="en">
             <descrip type="definition">Corrective lenses whose optical power increases continuously from the top of the lens to the bottom.</descrip>
             <tig>
               <term>progressive lens</term>
               <termNote type="administrativeStatus">preferredTerm-admn-sts</termNote>
             </tig>
             <tig>
               <term>PAL</term>
               <termNote type="administrativeStatus">admittedTerm-admn-sts</termNote>
             </tig>
             <tig>
               <term>no-line bifocal</term>
               <termNote type="administrativeStatus">deprecatedTerm-admn-sts</termNote>
             </tig>
           </langSet>
         </termEntry>
     ...
   </martif>
   ```

   Each language section takes its term's `language`, and the definition sits
   inside it. A term that declares none is written as `en`. `-f tbx3` writes
   the same entries as `<conceptEntry>`, `<langSec>` and `<termSec>`, under
   `<tbx type="TBX-Basic" style="dca">`. A set that carries a TBX-Linguist
   field, such as `register` or `transfer-comments`, is written as
   `TBX-Linguist`.

2. **Or write CSV.** A spreadsheet or a system that maps columns by header
   gets one row per entry. The per-language columns carry the language in
   their header, and a list field joins its values with ` | `:

   ```sh
   manni term write docs/terms/ -f csv -o build/terms.csv
   ```

   ```
   ID,Term [en],Definition [en],Abstract [en],Alt labels [en],Hidden labels [en],Scope note [en],Broader,Narrower,Related terms,See
   bifocal,bifocal,"Lenses with two distinct optical powers, divided by a visible line.",,,,,,,,
   progressive-lens,progressive lens,Corrective lenses whose optical power increases continuously from the top of the lens to the bottom.,Lenses that correct presbyopia without a visible line.,PAL,no-line bifocal,Spectacle lenses only. Contact lenses are out of scope.,,,bifocal,
   varifocal,varifocal,,,,,,,,,progressive-lens
   ```

   CSV holds the ten SKOS fields. A TBX field, such as `designations` or
   `concept-entry`, is reported dropped.

</Steps>

## Read the termbase back

The translation team returns the termbase with a German term for each
concept, grammatical gender, and a vendor field. This one is TBX v3:

```xml title="l10n/glossary.tbx"
<?xml version="1.0" encoding="UTF-8"?>
<tbx type="TBX-Basic" style="dca" xml:lang="en" xmlns="urn:iso:std:iso:30042:ed-2">
  <tbxHeader>
    <fileDesc>
      <sourceDesc>
        <p>Optics termbase, exported by the translation team.</p>
      </sourceDesc>
    </fileDesc>
  </tbxHeader>
  <text>
    <body>
      <conceptEntry id="progressive-lens">
        <descrip type="subjectField">optics</descrip>
        <descrip type="Client">Acme</descrip>
        <langSec xml:lang="en">
          <descrip type="definition">Corrective lenses whose power increases continuously.</descrip>
          <termSec>
            <term>progressive lens</term>
            <termNote type="administrativeStatus">preferredTerm-admn-sts</termNote>
            <termNote type="partOfSpeech">noun</termNote>
            <termNote type="termType">fullForm</termNote>
          </termSec>
          <termSec>
            <term>PAL</term>
            <termNote type="administrativeStatus">admittedTerm-admn-sts</termNote>
            <termNote type="termType">acronym</termNote>
          </termSec>
          <termSec>
            <term>no-line bifocal</term>
            <termNote type="administrativeStatus">supersededTerm-admn-sts</termNote>
          </termSec>
        </langSec>
        <langSec xml:lang="de">
          <descrip type="definition">Brillenglas mit stufenlos zunehmender Wirkung.</descrip>
          <termSec>
            <term>Gleitsichtglas</term>
            <termNote type="administrativeStatus">preferredTerm-admn-sts</termNote>
            <termNote type="grammaticalGender">neuter</termNote>
          </termSec>
          <termSec>
            <term>Gleitsichtbrille</term>
            <termNote type="administrativeStatus">admittedTerm-admn-sts</termNote>
            <termNote type="grammaticalGender">feminine</termNote>
          </termSec>
        </langSec>
      </conceptEntry>
      <conceptEntry id="bifocal">
        <langSec xml:lang="en">
          <descrip type="definition">Lenses with two distinct optical powers, divided by a visible line.</descrip>
          <termSec>
            <term>bifocal</term>
            <termNote type="administrativeStatus">preferredTerm-admn-sts</termNote>
          </termSec>
        </langSec>
        <langSec xml:lang="de">
          <descrip type="definition">Brillenglas mit zwei getrennten Wirkungen.</descrip>
          <termSec>
            <term>Bifokalglas</term>
            <termNote type="administrativeStatus">preferredTerm-admn-sts</termNote>
          </termSec>
        </langSec>
      </conceptEntry>
    </body>
  </text>
</tbx>
```

<Steps>

1. **See what is read.** Each language of an entry is a term of its own, with
   the entry's id. The list adds a language column when the set holds more
   than one:

   ```sh
   manni term list l10n/glossary.tbx
   ```

   ```
   progressive-lens   en   progressive lens   PAL
   progressive-lens   de   Gleitsichtglas     Gleitsichtbrille
   bifocal            en   bifocal
   bifocal            de   Bifokalglas
   4 terms
   ```

   A walk of a directory reads a `.tbx` file it finds, and `term.manifests`
   can list one. `-` reads one from stdin with `--as tbx`.

2. **Look at one term.** Every TBX data category has a named field. A value
   about the concept sits in `concept-entry`, and a value about one
   designation in its `designations` item:

   ```sh
   manni term get PAL l10n/glossary.tbx
   ```

   ```
   progressive lens                        l10n/glossary.tbx:15
     id               progressive-lens
     language         en
     alt-labels       PAL
     hidden-labels    no-line bifocal
     definition       Corrective lenses whose power increases continuously.
     concept-entry    subject-field: optics
     designations     progressive lens: part-of-speech noun, term-type fullForm
                      PAL: term-type acronym
                      no-line bifocal: administrative-status superseded
     tbx-elements     1 in concept-entry
     other languages  de (Gleitsichtglas)
   ```

   The vendor's `Client` field has no name in TBX-Basic, so it rides along
   whole in `tbx-elements`. The superseded term is a hidden-label that keeps
   its status. The [terminology reference](/manni/term/reference/terminology/#the-tbx-data-categories)
   has every field.

3. **Write it back.** In place, an unchanged termbase stays byte-identical. So
   does an export at the file's own version:

   ```console
   $ manni term write l10n/glossary.tbx
   Nothing to write
   $ manni term write l10n/glossary.tbx -f tbx3 -o build/same.tbx
   Wrote 4 terms to build/same.tbx
   $ cmp l10n/glossary.tbx build/same.tbx && echo identical
   identical
   ```

   `-f tbx` turns the v3 file into v2. The header carries over, and each
   entry is written in v2's element names:

   ```console
   $ manni term write l10n/glossary.tbx -f tbx -o build/glossary-v2.tbx
   Wrote 4 terms to build/glossary-v2.tbx
   ```

4. **Render the pages.** A set in more than one language puts each page under
   a directory named for its language:

   ```sh
   manni term write l10n/glossary.tbx -f markdown -o docs/glossary/
   ```

   ```
   Wrote 4 terms to docs/glossary/, one file each
     dropped from a page: the header of l10n/glossary.tbx
   ```

   ```markdown title="docs/glossary/de/progressive-lens.md"
   ---
   title: Gleitsichtglas
   type: term
   id: progressive-lens
   language: de
   label: Gleitsichtglas
   definition: Brillenglas mit stufenlos zunehmender Wirkung.
   alt-labels:
     - Gleitsichtbrille
   concept-entry:
     subject-field: optics
     tbx-elements:
       - <descrip type="Client">Acme</descrip>
   designations:
     - term: Gleitsichtglas
       grammatical-gender: neuter
     - term: Gleitsichtbrille
       grammatical-gender: feminine
   ---
   ```

   The pages hold every field. The file's header is not a term, so it stays
   behind, and the run says so.

5. **Hand the pages back as TBX.** The pages join on id into one entry per
   concept:

   ```sh
   manni term write docs/glossary/ -f tbx3 -o build/glossary.tbx
   ```

   ```
   Wrote 4 terms to build/glossary.tbx
   ```

   The entries come in the order the pages are read, and the walk reads
   `de/` before `en/`. The header is manni's own. Where the languages
   disagree on the concept, the entry keeps the first one read and the run
   names the field. Here the German page says `subject-field: Optik`:

   ```
   Wrote 4 terms to build/glossary.tbx
     kept the first language's value where languages differ: concept-entry.subject-field on 1 concept
   ```

### What a TBX round trip keeps

A TBX file's records survive any trip through manni. Read a termbase, write it
as `tbx` or `tbx3`, and read the result. Every field, `designations`,
`tbx-elements`, `tbx-markup` and `language` comes back equal.

The bytes survive at the file's own version. An unchanged entry is copied as it
was, and so is everything outside the entries. A file manni wrote exports
byte-identical. A file another tool wrote exports equivalent XML, differing
only in whitespace between elements, attribute order and quote style.

An entry whose record changed is written in manni's layout. It keeps its
attributes, and an `ntig` stays an `ntig`. It loses what sat outside the
record:

- the order of its children, which takes manni's order;
- a comment, a processing instruction or a CDATA section between its
  elements;
- a language section with no `<term>`;
- the layout of an `ntig`'s children;
- a DTD entity reference, which reads as its literal text and is written
  escaped.

Exporting to the other version writes every entry in manni's layout. It
carries the header and `<back>`, and drops the XML prolog. DCT style becomes
DCA, and an `ntig` becomes a `tig` or a `termSec`. Inline tags are not
converted between v2's `<bpt>`/`<ept>` and v3's `<sc>`/`<ec>`. `abstract`,
`broader`, `narrower`, `related-terms`, `see` and `scope-note` have no TBX-Basic
category, so a TBX render drops them and says so.

Only UTF-8 TBX is read.

## Write back in place

{/* cite no-f-writes-in-place */}
{/* cite in-place-reader-per-construct */}
{/* cite only-differing-entry-rewritten */}
{/* cite unchanged-page-byte-identical */}
With no `-f`, `manni term write` sends each entry back through the reader that
read it. Only an entry whose record differs from its file is rewritten. A set
read and written unchanged leaves every file byte-identical:

```console
$ manni term write docs/
Nothing to write
```

{/* cite body-construct-spliced */}
{/* cite page-rewritten-through-extractor */}
{/* cite dfn-has-no-writer */}
A body construct is spliced in place, and a page is rewritten through the
extractor that read it. An HTML `<dfn>` is the one construct that cannot be
written back:

```
manni: glossary.html: a dfn cannot be written in place. Pass -f <format> -o <path>.
```
