**Scope:** judging the turn that just ended against the rules your repository declares for agents,
and against what you asked for.
It serves Maya, and it follows [the post-hoc run](/manni/tracevals/get-started/), which grades a
whole session after the fact. For the files a session used, see
[artifact coverage](/manni/tracevals/declare/coverage/).

You wrote the rules. The agent read them. It still ran `npm test` in a fresh worktree before
`npm ci`, and you found out in the diff. Fixing it costs a review cycle and a new prompt. The rule
sat in the agent's context the whole time, and nothing told it.

`tracevals` can check at the end of every turn instead. It reads the rules files that govern the
agent, and what you asked it to do. It judges the last turn against the session so far, and names
each broken rule with the source it came from. The agent fixes the work, or says why the rule does
not apply, before the turn reaches you.

The same check catches a settings toggle you asked for and never got. It catches a task ticked with
no work behind it, and a skill's step run out of order.

## Set it up

<Steps>

1. Install the [`manni` plugin](/manni/family/claude-code/). It carries the hooks that run the check.
   To run the check by hand, skip this step.

2. Add one section to `manni.config.yaml`. An empty one is enough, and its presence is the switch.

   ```yaml title="manni.config.yaml"
   tracevals:
     conformance: {}
   ```

3. Choose the models. Two roles do different work, so each gets a model of its own.

4. Run `manni tracevals prepare` once. The first turn then finds its rules cached and its local model
   on disk.

</Steps>

Without a `conformance` section, tracevals stays out of every hook and `manni status` shows it as not
checked. To turn the check off, delete the section.

### Choose the models

Work inside the loop and outside it have different budgets.

| Role | Does | Set by |
|---|---|---|
| Out of the loop | Extracts rules from files, runs `prepare`, and judges `check` by hand | `tracevals.provider` and `tracevals.model` |
| In the loop | Judges a turn inside a Stop or SubagentStop hook | `tracevals.conformance.hook`, then the keys above |

The hook runs on every turn, so it wants a fast model. Extraction runs once per file version, so it
can afford a stronger one. These recipes are examples. tracevals pins no model.

```yaml title="Hosted: Sonnet out of the loop, Haiku in it"
tracevals:
  provider: anthropic
  model: claude-sonnet-5-5
  conformance:
    hook: { provider: anthropic, model: claude-haiku-4-5 }
```

```yaml title="Local: one model for both roles"
tracevals:
  provider: llama-cpp
  model: qwen3.5-4b
  conformance: {}
```

```yaml title="Jev judges each turn, a hosted model extracts"
tracevals:
  provider: anthropic
  model: claude-sonnet-5-5
  conformance:
    hook: { provider: jev, model: jev-latest }
```

Jev only decides, so it can judge inside a hook and can never be `tracevals.provider`. Its key comes
from `TYPESAFE_API_KEY`. Every key is in the
[configuration reference](/manni/tracevals/reference/configuration/#conformance).

## Which sources count

Resolution is deterministic, from the filesystem and the trace. No model decides which sources count.
A model only reads the sources that do and returns their rules.

The list of formats is closed. Each one is scoped by its own trigger, as the tool that owns it scopes
it.

| Format | Files | In scope when |
|---|---|---|
| Claude memory | `CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md`, and the one in your Claude config directory | Always for the working directory and its ancestors. A subdirectory's file applies once the session touches a file under it. |
| Claude rules | `.claude/rules/**/*.md`, and the same under your Claude config directory | Without `paths:`, always. With `paths:`, once the session touches a match. |
| `AGENTS.md` | `AGENTS.md` and `.claude/AGENTS.md`, nested too | As for Claude memory. |
| `GEMINI.md` | `GEMINI.md`, the one in `~/.gemini`, nested too | As for Claude memory. |
| Cursor rules | `.cursor/rules/**/*.mdc`, and `.md` files there with front matter | `alwaysApply: true` means always. `globs` means once the session touches a match. Others apply once the agent reads them. |
| Kiro steering | `.kiro/steering/*.md`, and the same under `~/.kiro` | `inclusion: always`, or none, means always. `fileMatch` follows `fileMatchPattern`. Others apply once read. |
| Spec Kit constitution | `.specify/memory/constitution.md` | Always |
| OpenSpec project | `openspec/project.md` | Once the agent reads it |
| Imports | Files an `@path` line pulls into a memory file, up to four hops | With the importing file |
| Skills, commands, agents | An invoked skill's `SKILL.md` and every file read under its directory, a slash command, and the running subagent's definition | A skill or command from its first invocation to the end of the session. A subagent's definition for its own run. |
| Designated | Files matching `conformance.include` | Always |

To touch a file is to read, write or edit it. That is Claude Code's own trigger for path-scoped
rules. `paths:`, `globs` and `fileMatchPattern` each accept one glob or a list. A nearer file
overrides a farther one, and a prompt you typed overrides any rule. Doing what you asked is never a
violation.

### Reading a file never makes it a rule

A README, a docs page, a design note or an API reference describes other systems or other readers.
Judging the agent against one would fail it for sentences never meant for it. Two things keep those
out.

- **The list of files.** It is closed. `include` adds files you name, and it is empty by default.
  A repository whose `CLAUDE.md` tells agents to consult `docs/content-strategy/` would name that
  tree there.
- **The sentences.** Extraction keeps only directives addressed to the agent working in the repo.
  A description of a system, an instruction for end users, an example or a quoted rule yields
  nothing. A skill reference that documents an API yields no rules, though its skill counts.

`exclude` removes a file from every row, for a product docs tree or a stale `.cursor/rules` file.
That covers plan, spec and output style files too.

### Spec-driven toolkits

Three spec-driven toolkits keep agent guidance apart from specs, and tracevals reads both. Spec Kit's
constitution, Kiro's steering files and OpenSpec's `project.md` govern the agent, as the table above
says. Their specs say what to build. Each counts once the session touches it, as
[What the session was asked](#what-the-session-was-asked) says.

### What a rule looks like

Each rule has an id, its text, and a `when`. The id is kebab-case, or a spec's own id. The `when`
uses the same grammar as
[conditional triggers](/manni/tracevals/reference/graders/#conditional-triggers), so a rule about
commands arms only for the turns that ran one.

```json
{ "id": "run-npm-ci-first",
  "text": "Run npm ci first when working in a worktree.",
  "when": { "command-matches": "\\bnpm (test|run)\\b" } }
```

A rule a transcript cannot show, such as "prefer boring code", is dropped. A file that declares its
own `ai` evals is not extracted. Its eval assertions are its rules, with their own `when`.
Extraction is cached under `.manni/tracevals/cache/rules`. The key is the provider, the model, the
extraction prompt and the sha256 of the whole source. So a source pays for extraction once per
version. Rules files and the sources from what you asked are read by two different prompts.

## What the session was asked

A rules file says how to work. What you asked for says what to build, and a turn can call that work
done when it is not. Six more formats carry it.

| Format | Source | In scope when |
|---|---|---|
| Typed prompts | Every prompt you typed in the session, read as one numbered sequence | Always |
| Approved plan | The plan of the last approved `ExitPlanMode`, from its input or the plan file written before it | From the approval on |
| Spec Kit spec | `specs/<feature>/spec.md`, `plan.md` and `tasks.md` | Once the session touches a file under `specs/<feature>/` |
| Kiro spec | `.kiro/specs/<name>/requirements.md`, `design.md` and `tasks.md` | Once the session touches a file under that directory |
| OpenSpec change | Every `.md` file under `openspec/changes/<id>/` | Once the session touches a file under that change. An archived change never counts. |
| Plans | A file that `conformance.plans` names | Once the session touches it |

- **Prompts.** Extraction returns the items that stand after your last prompt, so "forget the toggle"
  drops the toggle. A question with nothing to build yields no rules. Each new prompt costs one
  extraction.
- **A plan.** A later approval replaces the plan. A rejected plan never counts.
- **Specs.** Only a touched feature counts, so a tree of many specs brings in only the one in play.
  A rule keeps the spec's own id, such as `FR-001`, `T014` or `1.2`.

Plans in a format of your own go in `conformance.plans`. A folder of plans holds plans for other work
too, so a file counts only once the session touches it. `include` is for files that govern every
turn, which is why plans have a key of their own.

```yaml title="manni.config.yaml"
tracevals:
  conformance:
    plans: [docs/plans/*.md]
```

`exclude` removes a plan or spec file here too. Your typed prompts are not a file, so a glob never
matches them. `exclude` drops them by the name `prompt`, and a plan given only as input by `plan`.

A rule from what you asked is judged like any other. "Add a dark mode toggle" does not apply yet
while the work goes on. It is followed once the toggle exists. It is broken on the turn that says
the work is done without one.

### Ticks

A ticked task is the agent saying that task is done. An Edit that turns `- [ ] T014 …` into
`- [x] T014 …` is a tick. Spec Kit, Kiro and OpenSpec all keep tasks this way. The judge sees each
earlier tick by its id, so a tick with nothing behind it reads as a claim to check. A `Write` that
rewrites the whole tasks file is not read as a tick.

## The system prompt the session ran under

Claude Code records its system prompt in the transcript, as a `prompt_snapshot` entry. It writes one
at session start, and again after a compaction or a resume. tracevals reads the last one at or before
the turn as one more source, `system-prompt`. A session that records none has no such source, and
there is nothing to configure.

Who wrote the prompt decides what a break does.

| Prompt | How tracevals tells | A break |
|---|---|---|
| Claude Code's default | It holds Claude Code's boundary marker. | Reported with `!` by `tracevals check`. It never blocks and never fails `check`. A hook skips it. |
| Replaced, with `--system-prompt` or `--system-prompt-file` | The boundary marker is missing, and the trigger ends `, custom`. | Blocks, like any rule. |
| A user output style | A file under `.claude/output-styles/` or `~/.claude/output-styles/` defines it. | Blocks, under the style file's path. |
| Appended, with `--append-system-prompt` or `--append-system-prompt-file` | It cannot be told apart. It is a last block with no name, as the desktop app's own block is. | Counts as default, so it is reported. |

- **An output style.** A user style is a source of its own, and its trigger is `style <name>`. Its
  content is the text the transcript recorded, which is what the agent saw. A built-in style has no
  user file, so its text joins the default prompt.
- **Redaction.** The prompt names paths under your home directory. So
  [`judge.redact`](/manni/tracevals/reference/configuration/#judge) scrubs the prompt and a style's
  text before extraction.
- **Cost.** Extraction is cached by the redacted text, so one Claude Code version pays once per
  project. The default prompt yields many rules. A Stop or SubagentStop hook never extracts or judges
  them, because a warning could not block. Run `tracevals check` to see them.
- **The judge.** A rule from the system prompt is a default. A rules file, or a prompt you typed,
  overrides it.

The fixture's default prompt says never to claim the tests pass without showing them, and its last
turn does.

```console
$ cd ../project
$ manni tracevals check ../traces/system-prompt.jsonl --project . --no-cache
system-prompt
  ! never-say-tests-pass-without  Never say `Tests pass` without showing the test output.
      not-followed 100, followed 0, not-applicable 0. The turn shows `Tests pass`. (1.00)

Last turn of 3b265d00: 7 rules from 4 sources. None broken, 1 reported.
```

The `!` row is a confident break of a default rule. The closing line counts it as reported, and the
command exits `0`. The same rule in a replaced prompt prints `✖`, and the command exits `1`.

To leave the system prompt out, name it in `exclude`. The names `prompt`, `plan` and
`system-prompt` match as whole names, never as globs, so `**` keeps them.

```yaml title="manni.config.yaml"
tracevals:
  conformance:
    exclude: [system-prompt]
```

## Procedures are rules

A skill's procedure is rules too. Extraction keeps its sentences about the order of steps, a gate one
step must pass before another, and a route a step's result chooses. It also keeps a condition that
calls for a step, a required step, and the step that comes last. The judge reads each one against
what the session did, which names every skill call and every agent spawn with its result.

```json
{ "id": "follow-reviewer-route",
  "text": "Send the draft to the pass the Reviewer names in route_to." }
```

A skill's rules stay in scope from its first invocation to the end of the session. A skill it calls
partway through does not end that. A slash command's rules work the same way. The post-hoc
`manni tracevals run` still grades each skill against its own window.

## What the agent sees

At Stop, the hook judges the turn with the in-loop model. Only a confident violation blocks.

- **A broken rule.** The hook blocks the stop once. The reason is the report above, with color off.
  The agent fixes the work, or says why the rule does not apply here, and finishes.
- **A broken default.** A rule from Claude Code's default prompt never blocks. When another rule
  blocks, the report shows the default's break with `!`. The count in the reason leaves it out.
- **A rule the model could not settle.** It shows as needs-review in `check`. It never blocks, and it
  never fails `check`.
- **A rule still broken after the repair pass.** The agent stops, and you see one message.
  It names `manni tracevals check` and the transcript, so you can read what remains.

```json
{"decision":"block","reason":"This turn broke 1 rule from the files and requests that governed it. Fix the work, or say why the rule does not apply here, then finish.\n\n<report>"}
```

The repair pass judges the whole turn once more. The turn has grown, so the verdict cache misses, and
the pass costs one call. It is the only way to tell you a rule is still broken.

The judge asks about each rule on its own. It sees the last turn, what the session did before it,
and that one rule. It first says in a sentence or two what the session shows about the rule. Then
it returns three scores from 0 to 100: not applicable, followed, and not followed.

The scores read different spans. A rule applies once the session does the kind of work it covers,
and followed reads the whole session. Not followed reads only the last turn. A rule is broken for
what the last turn did, or for the last turn saying the work is done without it. So an old break
blocks once. A later turn that neither repeats it nor claims the work is done does not block again.
The three are independent, so a long record of keeping a rule never hides a break in the last turn.

Some rules cover a procedure that spans turns, such as running `npm ci` once before any test. So
every call opens with what the session did before the last turn, read from the transcript. Each
earlier turn gets a line with its commands, the files it wrote, the rule files it read and its skill
calls. The line also names each agent it spawned, with the first line of the result. It names a
question to you, each task it ticked and a plan you approved. So `npm ci` run three turns ago still
counts.

```text
# Earlier in this session

- turn 40: ran npm ci; ran skill authoring-workflow
- turn 52: spawned technical-nonfiction-reviewer, which returned {"route_to":"writer","issues":[…
- turn 61: wrote specs/001-login/tasks.md; ticked T014 in specs/001-login/tasks.md
```

That block takes at most a quarter of the judge's budget. In a long session its oldest lines go
first, and a marker line says which turns went.

The hook also keeps a ledger for each session. It records each turn's facts and each judged rule's
results. Each rule shows the judge its earlier results, and keeps its first `followed` and every
`broken` one in view. The ledger marks a stretch of turns that left the rule's file out of scope.
So the judge can tell a gap from a quiet history. A subagent keeps a ledger of its own.

`manni tracevals check` reads a session's ledger and never writes it. Its `Session so far` section
names each rule that was ever broken or needed review, and counts the rest.

```text
Session so far
  CLAUDE.md#run-npm-ci-first  broken 1, repaired 1, followed 6
  31 rules held every turn they applied to.
```

The ledger's shape is in
[Report and exit codes](/manni/tracevals/reference/report-and-exit-codes/#the-session-ledger).

Only a confident violation blocks. A rule blocks when its not-followed score reaches
[`judge.zones.autoFail`](/manni/tracevals/reference/configuration/#judge) as a percentage, in every
run, and no run errored. It passes when its not-applicable or followed score reaches
`judge.zones.autoPass` in every run. Anything else needs review, including a rule the judge errored
on. `conformance.hook.runs` sets the number of runs in a hook, and it defaults to `1`. Jev only
returns probabilities, so it makes one call, and each option's probability becomes its score.

<Aside type="note" title="A subagent is judged on its own">
SubagentStop judges the subagent's whole run, alone, with the same rules and the same bar. The
agent's own definition counts as a rule source for that run. Parallel subagents each get a judgement.
</Aside>

### When tracevals stays out of the way

A Stop runs a short list of cheap checks in order, and the first one that finds nothing to do ends
the run. Most of them are silent.

- No `conformance` section means tracevals never runs.
- A judge's own session never judges itself. tracevals sets `MANNI_TRACEVALS_JUDGE` on every process
  it spawns, so a `claude-cli` judge cannot set off the hook again.
- An empty turn, or one with no rule source in scope, ends the run. Your typed prompts are a
  source, so a turn rarely has none.
- A turn where every rule's `when` fails is skipped, never passed.
- A turn already judged, with the same rules, history and model, reuses its cached verdict.

Three local-model cases speak, once per session, and judge nothing. The model is still downloading,
or it is not on disk, or it does not fit in free memory. Each message says which. A hosted model skips
all three.

## Prepare, release and the model host

`manni tracevals prepare` fetches a local model that is not on disk and extracts the rules of every
file that applies to every session. The plugin runs it in the background at session start, so it
never holds the session up. The first turn then finds both ready. Prompts, plans and specs are not
known at session start, so the turn that first has them extracts them.

A local model loads once and stays loaded in a **model host**. That is one background process per
machine and user. Every hook is its client, and requests queue in the order they arrive. Without the
host, each Stop would pay a model load, and parallel subagents would each load their own copy.

A session takes a lease on the host when it starts, and `manni tracevals release` returns it at
session end. A model stays loaded while a lease is held and used within `providers.llama-cpp.keepAlive`,
which defaults to `10m`. A crashed session's lease lapses when it goes idle. With no lease left, the
model unloads, and the host exits when nothing is loaded.

By hand, `check` uses a host that is running and never starts one, so CI and one-off runs leave no
process behind. To free the memory right now, run `manni tracevals release --all`.
