import { Steps, Aside, LinkCard, CardGrid } from '@astrojs/starlight/components';

Your pages and the code they describe live in one repository. This page wires
`manni cite` into it once, so that a bare `manni cite check` covers the right
pages and finds the right sources. That is the whole of the setup for a single
repository. There are two more pages beside this one for the repositories that
need more.

[Get started](/manni/cite/get-started/) teaches the loop, meaning pin, check,
read the finding, fix, re-pin. This page is the repository around that loop.

Every transcript below is real output from the built tool.

## What you configure, and what you do not

| Thing | Where it comes from |
| --- | --- |
| Which pages are checked | A [collection](/manni/meta/reference/configuration/#collections) in `manni.config.yaml`, read by every manni tool. |
| Where `source.file` resolves from | The git root, unless you say otherwise. One repository rarely says otherwise. |
| Where an entry is written | The page's frontmatter, unless a collection declares a [sidecar manifest](/manni/cite/reference/citations/#the-sidecar). |
| Which findings fail the build | The default [severities](/manni/cite/reference/configuration/#severity), unless the team moves one. |

<Steps>

1. **Declare the pages as a collection.** `collections:` is a top-level key of
   the family's one config file, not a `cite:` key. Every tool reads it, so
   the pages you validate metadata on are the pages you check citations on:

   ```yaml title="manni.config.yaml"
   collections:
     - name: docs-pages
       paths: ["docs/**/*.md"]
       exclude: ["docs/drafts/**"]
   ```

   `paths` and `exclude` are globs, relative to the config file. With this in
   place, `manni cite check` with no arguments covers every declared
   collection, and `--collection docs-pages` narrows a run to one of them.
   Named paths on the command line beat both.

   Every key of a collection is in the metadata tool's
   [configuration reference](/manni/meta/reference/configuration/#collections).
   The `cite:` keys, all six of them, are in the
   [configuration reference](/manni/cite/reference/configuration/#keys) for
   this tool.

   <Aside type="note" title="A config with no cite: section is still a config">
     A file that declares `collections:` and nothing else is this tool's
     config. The documents are declared, and every `cite:` key takes its
     default. Add a `cite:` section when you want to move one of them.
   </Aside>

2. **Leave the root alone.** A `source.file` is a path relative to one root,
   settled once per run. In a single repository that root is the git root
   above your working directory, which is what you want, so there is nothing
   to set. `cd docs && manni cite check` reaches the same sources as a run
   from the top.

   You find out when the root is wrong, because the source end reads
   `missing` rather than resolving to the wrong file:

   ```
   ✗ docs/limits.md
       ✗ fetch-timeout   :16 current   lib/limits.ts:2 missing

   1 file checked, 0 passed, 1 failed, 1 finding
   ```

   Where git is available, sources resolve through tracked files only, from
   `git ls-files`, under a realpath containment check. So a file you have not
   committed is `missing` too. Without git, a directory walk stands in, and an
   uncommitted file resolves. [Where sources resolve from](/manni/cite/reference/cli/#where-sources-resolve-from)
   has the full order, and `--root` is how a second checkout is reached.

3. **Mint the first citation.** `add` takes the page with its lines, then the
   source with its lines. `--dry-run` prints the diff and writes nothing:

   ```sh
   manni cite add docs/limits.md:6 lib/limits.ts:2 --id fetch-timeout --dry-run
   ```

   ```diff
   --- docs/limits.md
   +++ docs/limits.md
   @@ -2,2 +2,12 @@
    title: Limits
   +citations:
   +  - id: fetch-timeout
   +    claim:
   +      lines: 3
   +      integrity: sha256-921b21cccab21a4577f224ec4171aa56a3414bb3a5a4704ab8b6f314c46aa094
   +    source:
   +      file: lib/limits.ts
   +      lines: 2
   +      integrity: sha256-78af1d3321f9cbb177a7e4c958e39be56fd14cb93c1e441778bc4232e0fe4b1f
   +      commit-sha: 9265563d8ea84a13fea0001b7e531c119f47d070
    ---
   ```

   Drop `--dry-run` to write it. The report names both pins and the line each
   end sits on:

   ```
   docs/limits.md: added fetch-timeout to frontmatter (claim at line 16, sha256-921b21cc…; source lib/limits.ts:2, sha256-78af1d33…, 9265563)
   ```

   You typed line 6 and the report says line 16, because the entry pushed the
   sentence down by ten lines. The entry itself stored `lines: 3`, which
   counts the page body rather than the file, so editing the frontmatter never
   moves a claim. [Body lines and file
   lines](/manni/cite/reference/citations/#body-lines-and-file-lines) states
   the rule once.

4. **Run the first check.** With the collection declared, no arguments are
   needed:

   ```sh
   manni cite check
   ```

   ```
   ✓ docs/limits.md
       ✓ fetch-timeout   :16 current   lib/limits.ts:2 current

   1 file checked, 1 passed, 0 failed, 0 findings
   ```

   Both ends read in file lines, whatever the entry stored. `-q` hides the
   clean files once the corpus is larger than a screen. [Read a
   result](/manni/cite/get-started/#read-a-result) decodes the row, and
   [Fix a failing check](/manni/cite/fix/) decodes every status it can carry.

5. **Commit the page and the config, then gate it.** `manni cite check` is
   something CI runs on every push, next to the metadata gate.
   [Run it in CI](/manni/cite/ci/) has the workflow, the output formats and
   the exit-code contract. It also has the baseline, which lets an existing
   backlog ramp in rather than block the first pull request.

</Steps>

## When nothing is declared and nothing is named

{/* cite no-inputs-is-an-error */}
{/* cite no-inputs-exits-2 */}
A run with no positional paths and no config is an operational error, exit
`2`, rather than a silently empty pass:

```sh
manni cite check --no-config
```

```
manni: No files to check. Pass paths/globs, or declare a collection under `collections:` in manni.config.yaml.
```

{/* cite update-shares-input-model */}
That is the metadata tool's [shared input
model](/manni/meta/reference/cli/#shared-input-model), which `check` and
`update` both follow. `add` is the exception, because it takes one page and
one source rather than a set.
