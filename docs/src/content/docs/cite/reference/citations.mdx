A citation pins a sentence on a page to the source lines it was written from.
The pin is a hash of those lines and the commit the hash was taken at. This
page is the vocabulary as the tool ships it. The schema it implements is
`manni:citations:1.0.0-proposal.2`, which adds encrypted sources to
`proposal.1`. The metadata tool publishes `proposal.1` as the tenth member of
its vocabulary family, and both drafts are open for review. The first draft
and its design notes are on the [proposal page](/manni/meta/proposals/citations/).

## Two channels

A page can carry citations in two places, and both are read, validated and
checked. Neither wins over the other; a collision is a finding.

- **Frontmatter.** A `citations` list, one entry per pinned range, plus an
  optional `citation-commit` that every entry without its own `commit`
  inherits. The metadata tool's `validate` sees this channel, and validates
  it when the schema is in the page's set.
- **Inline.** A statement in the body, written in the format's own comment
  syntax. It holds either a full entry as JSON or an id that refers to a
  frontmatter entry. Only `manni cite` reads this channel; it validates the
  payload itself, with Ajv against a bundled copy of the entry schema.

```yaml title="docs/limits.md (frontmatter)"
citation-commit: 3f9c2a1e7b0d4c5a6f8e9d0b1a2c3d4e5f607182
citations:
  - id: fetch-timeout
    src: lib/limits.ts:2
    integrity: sha256-78af1d3321f9cbb177a7e4c958e39be56fd14cb93c1e441778bc4232e0fe4b1f
    claim: The fetch timeout is 10 seconds.
  - src: lib/limits.ts
    integrity: sha256-aebba92f…
```

The second entry is a **bare pin**. It has no claim, no id, and no quote. It is legal,
and it is checked source-side only. It says this page rests on this file,
tell me when it changes, which is `source-of-truth` from the stewardship
vocabulary at line granularity. The two exist because they answer at
different grains.

## Page keys

| Key | Type | Description |
|---|---|---|
| `citations` | non-empty list of entries | One entry per pinned range. A page with no citations omits the key; an empty list is not a declaration. Ids are unique within the page, and a duplicate is `entry-invalid`. |
| `citation-commit` | commit | The commit every entry that omits its own `commit` was pinned at. An entry's own `commit` wins for that entry. There is no third place a commit can come from. |

Any other key at the page root that starts with `citation-` is rejected by the
schema. So a misspelled `citation-comit` fails the way a closed container
would make it. The root stays open for sibling vocabularies.

## Entry fields

An entry is a closed object. `src` and `integrity` are required; the rest
anchors the pin to the page.

| Field | Type | Required | Description |
|---|---|---|---|
| `src` | source reference | yes | The cited lines: `path`, `path:L` or `path:L1-L2`, with the path repo-root-relative and posix, and lines 1-based and inclusive. `path:L` is the canonical spelling of one line; `path:L-L` is accepted and never written. A bare `path` pins the whole file. A `~` ciphertext stands in for the path of a private source. See [the `src` grammar](#the-src-grammar). |
| `integrity` | `sha256-` and 64 lowercase hex digits | yes | The pin, which is the cited lines hashed under [the one rule](#the-hashing-rule). A keyed HMAC when `src` is encrypted. |
| `commit` | 7 to 40 lowercase hex digits | no | The commit the pin was minted at. Overrides `citation-commit` for this entry. The tool writes forty and prints seven; a person may type seven. Without one, a check can say the lines changed, but not since when, nor whether the pin was ever true. |
| `id` | `^[a-z0-9][a-z0-9-]*$`, unique per page | no | What an inline reference names, what a finding is reported under, and what `update --only` selects. Required in practice the moment the body points at the entry or the same claim occurs twice. |
| `claim` | non-empty string | no | The sentence the citation supports, verbatim. The tool finds it in the body with whitespace collapsed, so a soft-wrapped sentence matches, and reports the citation at that line. Punctuation is not whitespace: a comma where the claim has a full stop is a miss. |
| `quote` | boolean, default `false` | no | The page reproduces the cited lines in a fenced block, and that block is the anchor. The block is compared with the source under the same rule the pin uses. A quoted snippet that drifts from its source is `quote-drift` even while the pin holds. |

The metadata tool's `validate` checks the shape; it cannot check the pin.
Whether the hash still holds is a comparison against the source, and that is
what `manni cite check` adds.

## The `src` grammar

```
path
path:L
path:L1-L2
~CIPHERTEXT
~CIPHERTEXT:L
~CIPHERTEXT:L1-L2
```

A `path` is relative to the [root](/manni/cite/reference/cli/#where-sources-resolve-from),
posix-separated, and free of `.` and `..` segments. Segments may hold spaces
and dots, so `docs/release notes/v1.2.md:4-9` is a source. The grammar
rejects a leading `/`, a drive letter, a backslash, an empty segment, a URL,
and line `0`. It also rejects a ciphertext shorter than 82 characters, or one
holding a character outside base64url. So a source that could
never resolve fails at the schema rather than resolving to nothing. Lines are
1-based and inclusive. That the end line is not before the start line is the
tool's rule, since a pattern cannot compare two numbers. `path:9-3` is refused
by `add` and is `entry-invalid` on a page.

The pattern, as the schema spells it:

```
^(?:~[A-Za-z0-9_-]{82,}|(?!~)(?:(?!\.\.?(?:/|:|$))[^/\\:\r\n\t]+)(?:/(?:(?!\.\.?(?:/|:|$))[^/\\:\r\n\t]+))*)(?::[1-9][0-9]*(?:-[1-9][0-9]*)?)?$
```

### Encrypted sources

`~` followed by at least 82 base64url characters is an **encrypted** source.
The ciphertext is the path, spelled exactly as a plain `src` would spell it,
encrypted under the family encryption key. The line forms follow it unchanged.
Examples on these pages shorten it to `~AQm4…:2`, and the real value is
longer. The key is a top-level `encryptionKey:` in `manni.config.yaml`, or
`MANNI_ENCRYPTION_KEY`, which wins. [`manni key`](/manni/key/) sets it and
rotates it.

The encryption is deterministic AES-256-GCM in the `cite-src` context, so one
path under one key always gives one ciphertext.
[Proposal 0045](https://github.com/hawkeyexl/manni/blob/main/docs/proposals/0045-family-encryption-key.md)
states the construction. A checkout that has the key decrypts the path, then
checks it against the tracked files as it would a plain one. So a public docs
repository can cite a private code repository without publishing its paths.
The pin over an encrypted source is keyed, as [the hashing rule](#the-hashing-rule)
says. So the page also publishes no verifier a reader could run against a
guessed line.

Two things follow from the encryption being deterministic. A ciphertext is
stable across pages, so a public site does reveal how often one private file
is cited and when it moves. That is recorded as accepted. And `update` can
recognise one file across pages, because its ciphertext does not change. The
path is padded before encryption, so a ciphertext's length reveals only a
size class.

Without the key, `check` reports an encrypted citation `missing`, an error,
unless `--no-check-sources` skips it. Under another key it is `missing` too, because
the ciphertext does not decrypt.

## The hashing rule

Stated once, in the schema's `integrity` description, and implemented once:

> Decode as UTF-8. Drop one leading byte-order mark. Turn CRLF into LF. Split
> on LF and discard the empty element a trailing LF leaves. Take lines L1 to
> L2 inclusive, or every line for a bare path. Join with LF and no trailing
> LF. Keep trailing whitespace. A plain `src` hashes that text alone. An
> encrypted `src` carries a keyed pin instead: the HMAC-SHA256 of that text
> under a pin key derived from the encryption key.

The value is spelled `sha256-` and sixty-four lowercase hex digits, keyed or
not. The keyed pin can be compared, and it cannot be reversed. Two
consequences are worth knowing. A file's trailing newline is not a line, so
`path:1-7` and `path` over a seven-line file are one pin. And CRLF and a
byte-order mark are not changes, so a Windows checkout under `core.autocrlf`
reads every pin as current. A trailing space is a change, because it is one.

## Inline statements

One keyword, `cite`, and two payloads, in the format's own comment syntax, the
way Doc Detective writes its inline statements. The statement anchors what
follows it.

| Format | Forms | Payload allowed |
|---|---|---|
| markdown, mdx | `<!-- cite PAYLOAD -->`, `{/* cite PAYLOAD */}`, `[comment]: # (cite PAYLOAD)` | id in all three; JSON only in the first two |
| html, xml | `<!-- cite PAYLOAD -->` | id, JSON |
| asciidoc | `// (cite PAYLOAD)` | id only |
| rst | `.. (cite PAYLOAD)` | id only |

A payload that starts with `{` is **JSON**. It is a full entry, validated
against the same entry schema the frontmatter uses, with `claim` optional
because position is the anchor. Anything else must match the id grammar and
is a **reference** to the frontmatter entry with that id. `cite true` is a
reference to the id `true`, never JSON. Anything else is `statement-invalid`,
and so is JSON in a parenthesised form, whose closing `)` could sit inside a
JSON string. `add` writes the first form of each format.

The scanner looks for the open and close delimiters over the **body only**,
so a `cite` inside the frontmatter is never a statement. It also reads code
as code. An opener inside a fenced block or a backtick span is text, which is
how this page can show the syntax without carrying it. It reads at most 500
statements per page; past that, the rest are not read and the page carries
one `statement-invalid` saying so.

```md title="A reference, then a JSON entry, in markdown"
<!-- cite fetch-timeout -->
The fetch timeout is 10 seconds, and it is
not configurable.

<!-- cite {"src": "lib/limits.ts:3", "integrity": "sha256-…", "claim": "Retries default to 3."} -->
Retries default to 3.
```

```adoc title="A reference in asciidoc"
// (cite fetch-timeout)
The fetch timeout is 10 seconds.
```

```rst title="A reference in reStructuredText"
.. (cite fetch-timeout)
The fetch timeout is 10 seconds.
```

<Aside type="note" title="MDX pages">
An MDX page can use the `<!-- -->` form and the `{/* */}` form alike; the
tool treats `.md` and `.mdx` as one format. The JSX comment is the one MDX
itself accepts everywhere, so it is the safer choice on a page that renders.
</Aside>

## Anchoring

Every citation with a `claim`, a `quote` or an inline position anchors to a
place in the body, and that is the line a finding reports.

| Citation | Anchors to |
|---|---|
| A frontmatter entry with a `claim` and no reference | The one paragraph containing the claim, found with whitespace collapsed. Zero paragraphs is `claim-missing`; two or more is `claim-ambiguous`, with the remedy of an id and a reference statement above the intended one. |
| A reference statement | The rest of its own line when that carries text; else the paragraph that follows, through the next blank line or fence. The entry's `claim`, if it has one, must occur in that paragraph, else `claim-missing`. |
| An inline JSON entry | The same as a reference statement. Its own line, else the next paragraph, and its `claim` must occur there. |
| Any entry with `quote: true` | The fenced block that follows the statement (```` ``` ```` or `~~~` in markdown and MDX, `----` in asciidoc). A frontmatter entry with a `claim` anchors through the claim, and the first block after that paragraph must reproduce the range. A frontmatter entry with neither is matched against every block in the body. `html`, `xml` and `rst` have no fence the tool can locate, and `quote` there is `statement-invalid`. |
| A bare pin | Nothing. It is checked source-side only, and a finding on it reports the frontmatter entry's own line. |

A claim is matched **whitespace-normalized**: runs of whitespace on both sides
collapse to one space, so prose wrapped at eighty columns still matches.
Punctuation is verbatim. `add`, `check` and `update` share the one search, so
a claim `add` accepted is a claim `check` will find.

## Statuses and rules

`check` classifies each entry against its source, then applies the severity
table. A status is a finding when its rule's severity is not `off`; the
page-side rules are findings in their own right.

A severity is one of the family's three levels, or `off`. The defaults are in
the tables below, and
[`severity:`](/manni/cite/reference/configuration/#severity) in config moves
any of them.

| Severity | Reported | Fails the run | `github` | SARIF `level` | JUnit |
|---|---|---|---|---|---|
| `error` | yes | yes, exit `1`, unless baselined | `::error` | `error` | a `failure` |
| `warning` | yes | no | `::warning` | `warning` | a passing testcase |
| `notice` | yes | no | `::notice` | `note` | a passing testcase |
| `off` | no | no | nothing | nothing | nothing |

### Source-side statuses

| Status | Meaning | Message | Default |
|---|---|---|---|
| `current` | The range hashes to the pin. | `current` | `off` |
| `moved` | The pin does not hold at its range, and exactly one window of the same length elsewhere in the file hashes to it. `update` rewrites the `src`. A whole-file citation never moves. | `moved -> lib/limits.ts:4` | `warning` |
| `moved-ambiguous` | Two or more windows hash to the pin; the tool will not guess which. Widen the range. | `moved, 2 candidates (lib/limits.ts:4, lib/limits.ts:11); widen the range` | `error` |
| `changed` | No window hashes to the pin. With a commit and history: since when, and how many commits touched the path. With a commit git cannot show: `history unavailable`, plus one run notice about `fetch-depth: 0`. Where git is not available, a bare `changed`, plus one run warning. | `changed since 3f9c2a1, 2 commits` | `error` |
| `never-true` | No window of the range's length anywhere in the file at the recorded commit hashes to the pin, or the path was absent there. Asserted only when git can show that commit; a pin that held somewhere in that file was true when minted, so a later mismatch is `changed`. | `never true: the pin does not match at 3f9c2a1` | `error` |
| `missing` | The path is not a tracked file under the root (without git, not a file under it), or an encrypted source cannot be decrypted. A rename is `missing`; `add` is the remedy. | `missing`. An encrypted source says why: `missing (no encryption key is available to decrypt it)`, `missing (does not decrypt under the current key)` or `missing (no tracked file matches; wrong --root?)` | `error` |
| `skipped` | The sources were not read (`--no-check-sources` or `checkSources: false`). Not a finding; `json` carries the status. | `skipped` | none |

The move search runs whenever the pin does not hold, and history decides only
what a non-match is called. With the original text (git could show the
commit), candidates are the lines where the first line matches. Each
candidate is compared lexically and hashed on a full match. Without it, a
window of 2,000 lines either side of the pinned range comes first. Then the
rest of the file follows, under a 64 MiB hashing budget. Past the budget the
entry is `changed` with `truncatedSearch` set, and the run says so once. A
range longer than 5,000 lines is `entry-invalid`.

### Page-side rules

| Rule | Meaning | Default |
|---|---|---|
| `claim-missing` | The claim is not in the body, or not in the paragraph a reference statement anchors. | `error` |
| `claim-ambiguous` | The claim occurs in two or more paragraphs and nothing says which, or two statements reference one id. | `warning` |
| `statement-orphan` | A reference names an id no frontmatter entry has. | `error` |
| `statement-invalid` | The payload is neither an id nor JSON, is JSON where the form allows an id only, or is an entry the schema refuses. Also `quote` on a format with no fence, or more than 500 statements on a page. | `error` |
| `entry-invalid` | A frontmatter entry the schema refuses, a `citations` value that is not a list, or a `citation-commit` that is not a commit. Also a duplicate id, or a range longer than 5,000 lines. | `error` |
| `quote-drift` | `quote: true`, and no fenced block follows the statement, or the page has none. Or none of the blocks reproduces the cited lines, as pinned or as the source is now. | `error` |

Every rule reports under the id `manni:cite/<rule>`, which is the SARIF rule
id and the JUnit failure type. A baseline fingerprint is built from that
schema, the rule, the entry's position and a subject. The position is
`/citations/N` for a frontmatter entry and the root for an inline one. The
subject is the `id`, or the `integrity` when there is none. The subject
survives a move and a line shift and changes only on a re-mint, which is the
act that resolves the finding. A key rotation is the exception. Over an
encrypted source the `integrity` is the keyed pin, which `manni key rotate`
changes. Give such a citation an `id`, or re-record the baseline after a
rotation.

## The output rule

**Output never says more than the page did.** A finding, in every format,
spells a source exactly as the page spelled it: `~AQm4…:4`, never the path
it decrypts to. The decrypted path, the diff since the commit
and the commit subjects live on the result and reach output through the
`pretty` reporter only, under [`--reveal`](/manni/cite/reference/cli/#cite-check)
and `--show-diff`. `json`, `github`, `sarif` and `junit` never carry them, so
a public CI job can upload a SARIF log from a run that decrypted private
sources. A sentinel test runs every reporter against a fixture whose key and
private path are known strings, and asserts neither appears.

## Terms

| Term | Meaning |
|---|---|
| **citation** | One entry, made of a source range, its pin, and optionally the commit, an id, a claim and a quote flag. Lives in the frontmatter's `citations` list or in an inline statement. |
| **claim** | The sentence a citation supports, verbatim. What the check reports the citation at. |
| **pin** | The `integrity` value: the hash of the cited lines under the rule, at the moment the citation was minted. A record of the past, not a copy of the present, which is why it is stored rather than recomputed. |
| **statement** | A `cite` comment in the body, in the format's own syntax. Carries an id or a JSON entry, and anchors what follows it. |
| **reference** | A statement whose payload is an id. It points at the frontmatter entry with that id and anchors it to a paragraph. |
| **encrypted source** | A `~` and at least 82 base64url characters standing in for a path in `src`: the path, encrypted under the encryption key. Readable only where both the key and the files are. |
| **encryption key** | The family secret that encrypts private source paths and keys the pins over them. From `MANNI_ENCRYPTION_KEY`, else a top-level `encryptionKey:` in config. A `salt:` under `cite:` is refused. [`manni key`](/manni/key/) sets and rotates it. |
| **drift** | The gap between what a page says and what its source now holds. A `changed` citation is drift at the sentence; `quote-drift` is a reproduced block that no longer matches. |
