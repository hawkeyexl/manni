A citation pins one sentence on a page to the source lines it rests on. It
records a path and line range, a hash of those lines, and the commit they were
read at. manni cite then checks every pin against the source and tells you
which sentence stopped being true, not which page to re-read.

It runs from git alone. No model, no network, one hash per citation on a clean
run. A line that gained neighbours above it is `moved`, and one command fixes
that. A line whose bytes changed is `changed`, with the commits since, and a
person decides whether the prose or the pin is wrong.

## Three commands

| Command | Does |
| --- | --- |
| `manni cite add <page> <src>` | Mints a citation for a source range and writes it to the page, as a frontmatter entry or an inline statement. |
| `manni cite check [paths...]` | Classifies every citation as `current`, `moved`, `changed`, `never-true` or `missing`, and reports the findings through the same formats manni meta uses. |
| `manni cite update [paths...]` | Rewrites `moved` entries in place. With `--accept`, re-mints `changed` ones at HEAD. |

## A 30-second proof

You don't need to install anything. Say `docs/limits.md` claims that the fetch
timeout is 10 seconds, and that sentence rests on line 2 of `lib/limits.ts`.
Pin it:

```sh
npx @hawkeyexl/manni cite add docs/limits.md lib/limits.ts:2 --claim "The fetch timeout is 10 seconds." --id fetch-timeout
```

```
docs/limits.md: added fetch-timeout (lib/limits.ts:2, sha256-78af1d33…, 9265563) to frontmatter; reference at line 12, claim at line 13
```

Check it:

```sh
npx @hawkeyexl/manni cite check docs/limits.md
```

```
✓ docs/limits.md
    ✓ fetch-timeout   lib/limits.ts:2   current

1 file checked, 1 passed, 0 failed, 0 findings
```

Then someone raises the timeout to 30 seconds and commits. The page has not
changed, so metadata validation still passes. The citation check does not:

```
✗ docs/limits.md
    ✗ fetch-timeout   lib/limits.ts:2   changed since 9265563, 1 commit   (line 13)

1 file checked, 0 passed, 1 failed, 1 finding
```

Line 13 is the sentence. The exit code is `1`, so CI goes red on the line that
needs a person, and nowhere else. That's the whole loop: pin, check, read the
finding, fix the sentence, re-mint.

## What manni cite checks, and what it doesn't

<CardGrid>
  <Card title="It checks" icon="approve-check">
    That the lines a sentence cites are still the bytes they were when the
    citation was written. Where they went if they moved. What changed and in
    which commits if they did not survive. That every inline statement names a
    real entry, and every entry's claim is on the page.
  </Card>
  <Card title="It doesn't" icon="close">
    Judge whether the sentence was ever right, read the source for meaning, call
    a model, or reach the network. A `changed` finding is a question for a
    person; the check only makes sure it is asked about one sentence rather than
    a whole page.
  </Card>
</CardGrid>

Citations are written in the `manni:citations` vocabulary, which manni meta
publishes and manni cite implements. `manni meta validate` checks that an entry
is well-formed; only `manni cite check` can say whether it still holds. Both
tools ship in one package and read one `manni.config.yaml`, under their own
keys.
