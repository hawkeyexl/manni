import { Tabs, TabItem, Aside, LinkCard, CardGrid } from '@astrojs/starlight/components';

manni meta is a plain CLI with a stable exit-code contract. It drops into any CI
system that can run a Node.js command and read its exit code. This page gives
complete, runnable recipes for four common setups. The [GitHub Actions
gate](/manni/meta/ci/) is on its own page; the first recipe here adds persistence
on top of it.

Every recipe relies on the same contract. manni meta exits `0` when all files are
valid and `1` when one or more files fail validation. An operational or usage
error exits `2`. Each platform fails the job on a non-zero exit, so the gate is
enforced without extra scripting. For the full definition, see [Exit codes & PR
annotations](/manni/meta/ci/exit-codes-and-annotations/).

<Aside type="note" title="The github format is GitHub-specific">
`--format github` emits GitHub Actions workflow commands (`::error ...`). On
GitLab, Jenkins, and pre-commit it has no special effect; the lines print as
plain text. Use the default `pretty` output there, `--format junit` to feed the
platform's test reporter, or `--format json` to feed a tool of your own. The
annotation format is documented in
[Exit codes & PR annotations](/manni/meta/ci/exit-codes-and-annotations/).
</Aside>

## GitHub code scanning (upload-sarif)

`--format github` renders annotations on the pull request and then loses them
with the job log. `--format sarif` turns the same findings into **tracked
alerts** in the Security tab, with state across commits. That is what makes
"when did this regress" and "is our metadata debt going down" answerable.

```yaml title=".github/workflows/manni-sarif.yml"
name: manni meta code scanning
on:
  pull_request:
  push:
    branches: [main]

jobs:
  metadata:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      # Required by upload-sarif. Without it the upload fails with a 403.
      security-events: write
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '24'

      # continue-on-error is load-bearing: validate exits 1 when there are
      # findings, and the findings are precisely what is worth uploading.
      - name: Validate metadata
        id: manni meta
        continue-on-error: true
        run: npx -y @hawkeyexl/manni meta validate "docs/**/*.md" -f sarif > manni meta.sarif

      # if: always() so the upload still runs when the step above reported
      # findings. Without both of these, nothing is ever uploaded.
      - name: Upload to code scanning
        if: always()
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: manni meta.sarif
          category: manni meta

      # Optional: keep the job red so the gate still blocks the merge. Drop
      # this step to make code scanning purely informational.
      - name: Fail on findings
        if: steps.manni meta.outcome == 'failure'
        run: exit 1
```

<Aside type="caution" title="continue-on-error is not optional here">
This is the trap the recipe exists to avoid. `validate` exits `1` when it finds
anything. Without `continue-on-error: true` on the manni meta step and
`if: always()` on the upload, the job stops at the first finding. **The Security
tab then stays empty forever**, and the failing case is exactly the case with
something to upload.
</Aside>

<Aside type="caution" title="Run manni meta from the repository root">
GitHub resolves each `artifactLocation.uri` against the **repository root** and
silently drops results that do not resolve, so a bad path uploads successfully
with zero alerts. manni meta rebases paths onto the git root to prevent that, but
it needs the checkout to *be* a git repository. `actions/checkout` gives you
one. If manni meta warns on stderr that it could not make paths
repository-root-relative, the upload will report nothing.
</Aside>

A distinct `category:` namespaces the alerts, so manni meta's findings never merge
with another tool's. Give each SARIF-producing job its own.

## GitLab CI

Add a job to `.gitlab-ci.yml`. The official `node:24` image already has Node.js
and `npx`, so the job is a single script line. GitLab marks the job failed on
any non-zero exit, which is exactly manni meta's contract.

<Tabs>
<TabItem label="Explicit targets">

```yaml title=".gitlab-ci.yml"
validate-metadata:
  stage: test
  image: node:24
  script:
    - npx -y @hawkeyexl/manni meta validate "docs/**/*.md"
```

</TabItem>
<TabItem label="Targets from manni.config.yaml">

```yaml title=".gitlab-ci.yml"
validate-metadata:
  stage: test
  image: node:24
  # Targets come from paths: in manni.config.yaml at the repo root.
  script:
    - npx -y @hawkeyexl/manni meta validate
```

</TabItem>
</Tabs>

<Aside type="tip" title="Pin the version">
`npx -y @hawkeyexl/manni meta` resolves the latest published version on each run. Pin a
major for reproducible pipelines: `npx -y @hawkeyexl/manni@0 validate ...`.
</Aside>

If you collect machine-readable reports, capture the JSON output as an artifact:

```yaml title=".gitlab-ci.yml"
validate-metadata:
  stage: test
  image: node:24
  script:
    - npx -y @hawkeyexl/manni meta validate "docs/**/*.md" --format json | tee manni-report.json
  artifacts:
    when: always
    paths:
      - manni-report.json
```

`tee` writes the report to a file while passing manni meta's exit code through, so
the job still fails on validation errors. `when: always` keeps the artifact even
when the job fails.

For the merge request's **Tests** widget rather than a raw artifact, emit JUnit
XML and hand it to `artifacts:reports:junit`:

```yaml title=".gitlab-ci.yml"
validate-metadata:
  stage: test
  image: node:24
  script:
    - npx -y @hawkeyexl/manni meta validate "docs/**/*.md" --format junit | tee manni-junit.xml
  artifacts:
    when: always
    reports:
      junit: manni-junit.xml
```

Each file becomes one test, so the widget's count matches manni meta's
`N files checked, M failed` summary.

## Jenkins

Use a declarative `Jenkinsfile` stage. A `sh` step fails the stage when the
command returns a non-zero exit code, so the metadata gate works with no
explicit status check.

```groovy title="Jenkinsfile"
pipeline {
  agent any
  stages {
    stage('Validate metadata') {
      steps {
        // Requires Node.js 24+ on the agent (npx ships with npm).
        sh 'npx -y @hawkeyexl/manni meta validate "docs/**/*.md"'
      }
    }
  }
}
```

If your agents do not have Node.js 24+ on the `PATH`, provision it first. With
the NodeJS plugin installed and a tool named `node24` configured in **Manage
Jenkins → Tools**, wrap the stage:

```groovy title="Jenkinsfile"
pipeline {
  agent any
  tools {
    nodejs 'node24'
  }
  stages {
    stage('Validate metadata') {
      steps {
        sh 'npx -y @hawkeyexl/manni meta validate "docs/**/*.md"'
      }
    }
  }
}
```

To archive a machine-readable report, write JSON to a file and archive it. Run
manni meta in a way that preserves its exit code:

```groovy title="Jenkinsfile"
stage('Validate metadata') {
  steps {
    sh 'npx -y @hawkeyexl/manni meta validate "docs/**/*.md" --format json | tee manni-report.json'
  }
  post {
    always {
      archiveArtifacts artifacts: 'manni-report.json', allowEmptyArchive: true
    }
  }
}
```

To get manni meta into Jenkins' own **Test Result** page instead, emit JUnit XML
and pass it to the `junit` step:

```groovy title="Jenkinsfile"
stage('Validate metadata') {
  steps {
    sh 'npx -y @hawkeyexl/manni meta validate "docs/**/*.md" --format junit | tee manni-junit.xml'
  }
  post {
    always {
      junit 'manni-junit.xml'
    }
  }
}
```

`post { always { ... } }` matters for the same reason `if: always()` does in the
SARIF recipe. The run worth reporting is the one that failed.

## pre-commit

A pre-commit hook catches metadata errors before they reach CI. manni meta
publishes a [pre-commit](https://pre-commit.com/) hook, so the whole
configuration is three lines:

```yaml title=".pre-commit-config.yaml"
repos:
  - repo: https://github.com/hawkeyexl/manni
    rev: v4.0.0
    hooks:
      - id: manni meta
```

`rev` has to be a concrete tag, because pre-commit does not follow a floating
major the way `uses: hawkeyexl/manni@v0` does. So this is one place a copied
snippet really will go stale. Take the tag from [the latest
release](https://github.com/hawkeyexl/manni/releases/latest), and let
`pre-commit autoupdate` move it for you afterwards.

The hook fails the commit when manni meta returns a non-zero exit code. It already
knows which files to look at, covering every extension manni meta reads, matched
case-insensitively. You do not write a `files` pattern, and that matters more
than it sounds. A hand-written one is easy to narrow to `\.md$` and then quietly
stop checking the AsciiDoc and DITA in the same repo.

The hook needs nothing more to judge [managed stewardship
fields](/manni/meta/set-up/derived-metadata/), because `validate` compares a
stamp against the evidence on staged files too.

<Aside type="note" title="It needs Node on the machine">
The hook runs `npx @hawkeyexl/manni meta`, so contributors need Node 24 or newer on their
`PATH`. That is the same requirement as running manni meta anywhere else.
pre-commit does not install Node for it.
</Aside>

## pre-commit without the published hook

On an air-gapped machine, or under a policy against remote hook repos, you can
define a `local` hook instead of fetching from GitHub. You then own the `files`
pattern, so keep it in step with the formats you actually use.

<Tabs>
<TabItem label="Validate staged files">

```yaml title=".pre-commit-config.yaml"
repos:
  - repo: local
    hooks:
      - id: manni meta
        name: manni meta validate
        entry: npx -y @hawkeyexl/manni meta validate
        language: system
        # Run only on Markdown; pre-commit appends the staged file paths.
        files: \.md$
```

With `entry: npx -y @hawkeyexl/manni meta validate` and no positional paths in the entry,
pre-commit appends the list of staged, matched files as arguments. Each commit
then validates exactly what changed. `language: system` tells pre-commit to use
the `npx` already on your `PATH` rather than managing its own environment;
Node.js 24+ must be installed locally.

</TabItem>
<TabItem label="Validate the whole repo">

```yaml title=".pre-commit-config.yaml"
repos:
  - repo: local
    hooks:
      - id: manni meta
        name: manni meta validate
        entry: npx -y @hawkeyexl/manni meta validate "docs/**/*.md"
        language: system
        pass_filenames: false
        always_run: true
```

Set `pass_filenames: false` so pre-commit does not append staged paths, and
manni meta validates the fixed glob in the entry instead. `always_run: true` makes
the hook run even when no matching files are staged.

</TabItem>
</Tabs>

Install and test the hook:

```sh
pre-commit install              # wire the hook into git
pre-commit run manni meta --all-files   # run it across the repo once
```

<Aside type="tip" title="Prefer a documented one-liner?">
If you do not use the pre-commit framework, a plain Git `pre-commit` hook script
works too. Add `npx -y @hawkeyexl/manni meta validate "docs/**/*.md"` to
`.git/hooks/pre-commit` (and `exit` on its status). The commit aborts when
manni meta exits non-zero. This is a per-clone hook and is not shared through the
repository, which is why the pre-commit framework above is usually preferable.
</Aside>
