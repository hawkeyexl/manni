**Built-in id:** `manni:content-strategy:1.0.0`

Published at `https://hawkeyexl.github.io/manni/schemas/content-strategy/1.0.0.json`.
A `$schema` that names this URL resolves to the bundled copy, with no network
call.

**The question it answers: which audience does this persona belong to, and which persona does this journey belong to?**
A record is a page that declares `type: audience`, `type: persona` or
`type: journey`. [`manni strategy`](/manni/strategy/reference/cli/) reads
those records and holds pages to them. This vocabulary declares the two fields
that join the records, `audience` and `persona`, so `manni meta validate`
checks their shape.

The [audience vocabulary](/manni/meta/reference/schemas/manni-audience/)
is the other half. Its `audiences`, `personas` and `journeys` say who a page
serves. This vocabulary says how the records themselves hang together.

## Use it

Content-strategy is not in the
[default set](/manni/meta/reference/schema-resolution/#the-default-set), so a
run checks it only where the config names it. Declare a collection for the
records, then point an override at it. An override replaces the set unless it
sets `defaults: true`:

```yaml
collections:
  - name: strategy
    paths:
      - "docs/content-strategy/**/*.md"

meta:
  overrides:
    - collection: strategy
      defaults: true
      schemas:
        - manni:content-strategy:1.0.0
        - manni:content-strategy-strict:1.0.0
```

`manni strategy` reads every configured collection when it is given no paths,
so one declaration serves both tools.

## Records

A record is one page, in any format `manni meta` reads. Three types exist, and
the `type` value picks the kind.

| `type` | Names its parent with | The parent is |
|---|---|---|
| `audience` | nothing | none, an audience is the top of the tree |
| `persona` | `audience` | the `id` of an audience record |
| `journey` | `persona` | the `id` of a persona record |

`type`, `id`, `title` and `description` belong to
[`manni:core:1.0.0`](/manni/meta/reference/schemas/manni-core/) and this
vocabulary does not declare them. An `id` defaults to the file name without its
extension when a record has none.

An audience record:

```yaml
---
type: audience
id: docs-engineers
title: Docs-as-code teams
description: Docs-as-code teams own a docs repo and its frontmatter conventions.
---
```

A persona record names its audience:

```yaml
---
type: persona
id: maya
title: Maya, Documentation Engineer
description: Maya owns a docs-as-code repo for a platform product.
audience: docs-engineers
---
```

A journey record names its persona:

```yaml
---
type: journey
id: m5
title: Pin a claim and catch it going stale
description: A sentence on one of Maya's pages rests on a few lines of code.
persona: maya
---
```

## Fields

| Field | Type | Location | Notes |
|---|---|---|---|
| `audience` | string | `page` | The id of the audience a persona record belongs to. It is singular because a persona belongs to one audience |
| `persona` | string | `page` | The id of the persona a journey record belongs to. It is singular because a journey belongs to one persona |

No field is required. A persona with no `audience`, or a journey with no
`persona`, passes `manni meta validate`. The
[`orphan-record` rule](/manni/strategy/reference/rules/#the-rules) of
`manni strategy check` reports it while the set holds records of the parent
type.

Both fields are singular on purpose. The
[audience vocabulary](/manni/meta/reference/schemas/manni-audience/) has
`audiences`, `personas` and `journeys`, which mean who a page serves. Those
fields are references from a page. These two are the parent of a record, a
different relation. `personas` also carries the `external` location mark, so a
journey record that used it would draw a `location:external` warning. Both
fields here are `page`, so they stay in the record's own frontmatter.

The Location column is the `x-manni-location` mark each field carries. See
[field location](/manni/meta/schemas/field-location/) for how the marks are
used.

## Additional properties

Allowed. The root is open, so a generator's keys and the other vocabularies'
keys pass beside these two. The vocabulary checks only `audience` and
`persona`.

## A common mistake

A persona belongs to one audience, so a list fails.

```yaml
---
type: persona
id: maya
title: Maya, Documentation Engineer
description: Maya owns the docs build and its checks.
audience: [docs-engineers, sre]
---
```

```text
$ manni meta validate persona.md --no-config -s manni:core:1.0.0 -s manni:content-strategy:1.0.0
✗ persona.md
    /audience  must be string  (line 6)  [manni:content-strategy:1.0.0]
      manni:content-strategy:1.0.0 audience: The id of the audience a persona record belongs to.
      Guide: https://hawkeyexl.github.io/manni/meta/reference/schemas/manni-content-strategy/

1 file checked, 0 passed, 1 failed, 1 error
```

The exit code is 1. To place one persona in two audiences, write two persona
records with their own ids.

## Design decisions

- **The parent is a singular field on the child.** A record names its parent,
  and `manni strategy` derives the children by reading every record. A parent
  that listed its children would need an edit each time a child is added.
- **This vocabulary requires nothing.** The tool, not the schema, reports an
  orphan, because whether a parent should exist depends on the records in
  the set.
- **The ids are not checked against records here.** A schema judges one file
  and cannot see the others. `manni strategy check` reads the whole set and
  reports an `undefined-reference` when an id names no record.
- **The vocabulary is opt-in.** Most docs sets keep no strategy records, so the
  default set leaves it out.

## Strict overlay

**Strict overlay id:** `manni:content-strategy-strict:1.0.0`

Published at `https://hawkeyexl.github.io/manni/schemas/content-strategy-strict/1.0.0.json`.
The overlay holds only what strict adds. It narrows the form of a value that is
present and requires no key, so a record with neither field still passes it.

| Field | Strict adds |
|---|---|
| `audience`, `persona` | Kebab case, meaning lowercase letters, digits and hyphens that start with a letter or digit |

`strict: true` does not reach this overlay, because the vocabulary is not a
default. List the overlay beside its vocabulary, as the example under
[Use it](#use-it) does.

Each schema is checked on its own, and a finding names the one that produced
it. A strict-only failure reads as one.

```yaml
---
type: journey
id: m5
title: Pin a claim and catch it going stale
description: Maya pins a sentence to the code it describes.
persona: Maya Chen
---
```

```text
$ manni meta validate journey.md --no-config -s manni:core:1.0.0 -s manni:content-strategy:1.0.0 -s manni:content-strategy-strict:1.0.0
✗ journey.md
    /persona  must match pattern "^[a-z0-9][a-z0-9-]*$"  (line 6)  [manni:content-strategy-strict:1.0.0]
      manni:content-strategy-strict:1.0.0 persona: Strict holds the persona id to kebab case: lowercase letters, digits and hyphens, starting with a letter or digit.
      Guide: https://hawkeyexl.github.io/manni/meta/reference/schemas/manni-content-strategy/

1 file checked, 0 passed, 1 failed, 1 error
```

The open vocabulary accepts the value, so the overlay alone fails the record.
