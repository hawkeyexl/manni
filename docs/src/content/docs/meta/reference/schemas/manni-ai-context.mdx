**Built-in id:** `manni:ai-context:1.1.0`

Published at `https://hawkeyexl.github.io/manni/schemas/ai-context/1.1.0.json`.
A `$schema` that names this URL resolves to the bundled copy, with no network
call.

**The question it answers: how did machines make this page, and how may
they use it?** Two production fields, `provenance` and `meta-provenance`,
record what a machine wrote. Two consumption fields, `risks` and
`sample-questions`, speak to the agent that reads the page. Reach for it once
models write prose or metadata in your docs, or read them to act.

## Use it

AI context is in the
[default set](/manni/meta/reference/schema-resolution/#the-default-set), so a
run checks it on every page with no config line. A config's own `schemas` add
to the default set. An override replaces the set, so an entry that should keep
AI context sets `defaults: true`:

```yaml
meta:
  overrides:
    - collection: guides
      defaults: true
      schemas:
        - ./schemas/guide.json
```

## Fields

| Field | Type | Location | Notes |
|---|---|---|---|
| `provenance` | list of entries | `external` | Which body lines a machine wrote, one entry per range. Each entry names the machine, the lines, and an integrity hash that pins them. `manni meta derive` manages it |
| `meta-provenance` | list of entries | `external` | Per-model attribution of machine-proposed metadata, meaning which fields and evals, at what confidence |
| `risks` | string or list, open | `page` | Pre-flight flags for agents and reviewers. The seven recommended flags are `cost-incurring`, `destructive`, `irreversible`, `privileged`, `open-world`, `read-only` and `idempotent`. Any other non-empty string is valid |
| `sample-questions` | one item or a list | `page` | Questions a reader asks that should find this page. An item can also pin the lines that answer it. `manni graph check` asks them |

No field is required. Both lists of entries need at least one entry, with no
duplicates. `risks` takes one non-empty string, or a non-empty list of unique
ones. `sample-questions` takes one item, or a non-empty list of unique items.

A sample question is a non-empty string, or an object that requires
`question`. A string is a question this page must be found for.

| Key | Type | Notes |
|---|---|---|
| `question` | string, non-empty | The question, as a reader would ask it |
| `answers` | list of pins | The lines on this page that answer it. Without it, the page itself must be found |
| `generated-by` | string, non-empty | The model that drafted the question or any of its pins, as `provider/model` |
| `confidence` | number from 0 to 1 | The drafting model's confidence |
| `reviewed` | boolean | `false` marks a drafted question, and its pins are drafts with it. Absent means `true` |
| `reviewed-by` | string, non-empty | Who confirmed the question |

A pin in `answers` requires `lines`.

| Key | Type | Notes |
|---|---|---|
| `lines` | integer or string | One body line, or a range such as `"41-43"`, counted as a `provenance` entry counts them |
| `integrity` | string | `sha256-` and 64 lowercase hex digits over those lines. Without it, the lines are not checked for change |
| `reviewed` | boolean | `false` marks a pin nobody has confirmed, on a question that is itself confirmed. Absent means `true` |

Neither object takes any other key. [`manni graph
check`](/manni/graph/reference/cli/#graph-check) asks each question. A pinned one
must find the section that holds its lines, and a pin whose lines moved or
changed is reported.

A `provenance` entry requires all three of its keys.

| Key | Type | Notes |
|---|---|---|
| `generated-by` | string, non-empty | The model, agent, or tool that wrote the lines |
| `lines` | integer or string | One body line, or a range such as `"12-30"`. Lines count from the first line after the frontmatter |
| `integrity` | string | `sha256-` and 64 lowercase hex digits over those lines. It is the entry's identity |

A `meta-provenance` entry requires `generated-by` and at least one of `fields`
or `evals`.

| Key | Type | Notes |
|---|---|---|
| `generated-by` | string, non-empty | The model or agent that proposed the values |
| `fields` | list of strings | JSON Pointers to the values it proposed, such as `/intent` or `/graph/label` |
| `evals` | list of strings | Kebab ids of the evals it proposed |
| `confidence` | mapping | A number from 0 to 1, keyed by a pointer from `fields` or an id from `evals` |

Neither entry takes any other key.

The Location column is the `x-manni-location` mark each field carries. `page`
means the value belongs in the document's own metadata and reaches delivered
output. `external` means it belongs in the collection's
[external-metadata manifest](/manni/meta/set-up/external-metadata/). A field
is `page` when an agent fetching the page acts on it. `risks` and
`sample-questions` speak to an agent at read time. Both provenance records
describe how the page was made. See
[field location](/manni/meta/schemas/field-location/) for how the marks are
used.

## Additional properties

Allowed at the root. A generator's keys and the other vocabularies' keys pass
beside ai-context's, which checks only the four keys it claims. The entries in
`provenance` and `meta-provenance` are closed, and so are a sample question's
object and its pins. A misspelled key inside any of them fails.

## Example

The example keeps every field in the page to show them together. In a
collection with a manifest, the two provenance records sit in the manifest.

```yaml
---
title: Install the operator on Kubernetes
description: Deploy the operator with Helm and verify the rollout.
provenance:
  - generated-by: claude-fable-5
    lines: 4-18
    integrity: sha256-78af1d3321f9cbb177a7e4c958e39be56fd14cb93c1e441778bc4232e0fe4b1f
meta-provenance:
  - generated-by: claude-fable-5
    fields: [/intent, /sample-questions]
    confidence: { /intent: 0.9, /sample-questions: 0.84 }
risks: [privileged, cost-incurring]
sample-questions:
  - How do I install the operator on EKS?
  - question: Which Helm values enable the webhook?
    answers:
      - lines: 21-23
        integrity: sha256-43f97ea38783c4c88d2a558e429656b86aa00e3f5fcf5e5b284293cc41430496
  - question: How do I roll the operator back?
    answers:
      - lines: 30-32
    generated-by: anthropic/claude-sonnet-5-5
    confidence: 0.82
    reviewed: false
---
```

The first question must find the page. The second must find the section that
holds body lines 21 to 23. A model drafted the third, and nobody has reviewed
it yet.

## A common mistake

A `meta-provenance` entry that names a field by its key, not by a pointer,
fails.

```yaml
---
title: Install the operator on Kubernetes
description: Deploy the operator with Helm and verify the rollout.
meta-provenance:
  - generated-by: claude-fable-5
    fields: [intent]
---
```

```text
$ manni meta validate page.md --no-config -s manni:core:1.0.0 -s manni:ai-context:1.1.0
✗ page.md
    /meta-provenance/0/fields/0  must match pattern "^/"  (line 6)  [manni:ai-context:1.1.0]
    /meta-provenance  warning "meta-provenance" is stored in the page; manni:ai-context:1.1.0 prefers external metadata, and --no-config leaves it no manifest.  (line 4)  [location:external]

1 file checked, 0 passed, 1 failed, 1 error, 1 warning
```

The exit code is 1, and `/intent` fixes it. The warning is the `external`
mark, which fires because `--no-config` gives the page no manifest.

## Design decisions

- **Machines propose, and humans retire the record.** A `meta-provenance`
  entry is the review trail for machine-filled metadata. A human deletes the
  entry once its fields are reviewed, so a surviving entry means machine
  metadata nobody has checked. The same key serves the
  [graph](/manni/meta/reference/schemas/manni-graph/) block and both eval
  vocabularies, [evals](/manni/meta/reference/schemas/manni-evals/) and
  [artifact-evals](/manni/meta/reference/schemas/manni-artifact-evals/). So
  the whole family has one answer to "which of this metadata did a machine
  write, and has anyone checked?" [`manni meta fill`](/manni/meta/set-up/fill-providers/)
  writes an entry for the fields it fills.
- **`provenance` attributes the prose, and `meta-provenance` attributes the
  metadata.** They record different facts. `provenance` pins body lines by
  hash, and [`manni meta derive`](/manni/meta/set-up/machine-authorship/)
  stamps it from git. `lines` is where the pin was last seen, so a range that
  moves keeps its entry. A range whose text changes loses it.
- **The machines that wrote a page are derived.** They are the distinct
  `generated-by` values across its `provenance` entries, and there is no
  page-level `generated-by`. Consumers use them for self-preference-bias
  checks. A judge should know when it is grading its own author.
- **Humans never appear in `provenance`.** `authors` in
  [stewardship](/manni/meta/reference/schemas/manni-stewardship/) carries
  them.
- **`risks` is an open list.** Seven flags are recommended.
  `cost-incurring`, `destructive`, `irreversible`, and `privileged` cover
  operations. `open-world`, `read-only`, and `idempotent` mirror MCP's tool
  annotations, the published prior art for agent-facing hints. Any other
  non-empty string is valid. The assurances are worth stating, because an
  unannotated page has not been assessed, which is different from being safe.
  For the same reason, a consumer that branches on a flag treats an unknown
  value as a caution.
- **`sample-questions` closes the retrieval loop.** `manni graph check` asks
  each one through the retrieval `manni graph search` uses. It reports a page
  outside the top results for its own question. It measures finding, not
  answering. Per-page assertions belong to the evals vocabulary instead.
- **A pinned answer holds the question to the passage, not the page.** A long
  page can rank first for every question and prove nothing about the
  paragraph that answers one. A pin names those lines by hash, the way a
  citation does. So a rewrite that moves or changes the answer is reported,
  where an unpinned question would still find the page.
- **Review state travels with the question.** `reviewed: false` marks a
  draft, and a missing key means a person wrote or confirmed it. A pointer
  into `meta-provenance` would name a different question as soon as an
  earlier one was deleted. A pin has its own `reviewed`, so pairing a
  person's question with a drafted answer leaves the question confirmed.

## Strict overlay

**Strict overlay id:** `manni:ai-context-strict:1.0.0`

Published at `https://hawkeyexl.github.io/manni/schemas/ai-context-strict/1.0.0.json`.
The overlay holds only what strict adds. It narrows the form of a value that is
present and requires no key. A page with none of the vocabulary's fields
still passes it.

| Field | Strict adds |
|---|---|
| `meta-provenance[].generated-by` | A model id with no spaces, made of letters in either case, digits, `.`, `_`, `:`, `/`, `\`, `@` and `-`. `GPT-4o` and a Windows path to a local model pass |
| `meta-provenance[].fields` | Each pointer is well formed under RFC 6901, so every `~` begins `~0` or `~1` |
| `meta-provenance[].confidence` | Each key is such a pointer or a kebab eval id |
| `risks` | Closed to the seven recommended flags, in the string form and the list form alike |

`provenance` is the same in both. `manni meta derive` writes a commit
trailer's name there as git records it, such as `Claude Opus 5.5`.
`sample-questions` is the same in both too, which is why this 1.0.0 overlay
pairs with `manni:ai-context:1.1.0`.

`strict: true` stacks it right after the vocabulary, with every other
default's overlay beside its own base:

```yaml
meta:
  strict: true
```

To adopt this overlay alone, list its id. The default set already carries the
vocabulary:

```yaml
meta:
  schemas:
    - manni:ai-context-strict:1.0.0
```

Each schema is checked on its own, and a finding names the one that produced
it. A strict-only failure reads as one.

```yaml
---
title: Install the operator on Kubernetes
description: Deploy the operator with Helm and verify the rollout.
risks: [privileged, needs-vpn]
---
```

```text
$ manni meta validate page.md --no-config -s manni:core:1.0.0 -s manni:ai-context:1.1.0 -s manni:ai-context-strict:1.0.0
✗ page.md
    /risks/1  must be equal to one of the allowed values  (line 4)  [manni:ai-context-strict:1.0.0]

1 file checked, 0 passed, 1 failed, 1 error
```

The open vocabulary accepts `needs-vpn`, so the overlay alone fails the page.

## Version 1.0.0

**Built-in id:** `manni:ai-context:1.0.0`

Published at `https://hawkeyexl.github.io/manni/schemas/ai-context/1.0.0.json`.
It defines the same four fields, and a sample question is a string only. A
config that lists it replaces 1.1.0 in the default set. A page held to it that
pins an answer fails:

```text
$ manni meta validate old.md --no-config -s manni:core:1.0.0 -s manni:ai-context:1.0.0
✗ old.md
    /sample-questions/0  must be string  (line 5)  [manni:ai-context:1.0.0]
    /sample-questions  must match "then" schema  (line 4)  [manni:ai-context:1.0.0]

1 file checked, 0 passed, 1 failed, 2 errors
```

The same page passes under 1.1.0.
