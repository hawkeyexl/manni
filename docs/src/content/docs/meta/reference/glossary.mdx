The terms below are defined as manni meta uses them. Where a concept has a fuller
reference page, the entry links to it.

## frontmatter

A block of metadata at the very top of a document, set off from the body.
Markdown, MDX, AsciiDoc, and reStructuredText all accept the same fenced block
in any of three flavors: YAML (`---`), TOML (`+++`), or JSON (`;;;`). AsciiDoc
and rst fall back to a native header when no fence is present, using AsciiDoc
attributes or an RST field list. XML and HTML have no fenced form, because their
metadata lives in element attributes or head tags. A fenced block must be the
first thing in the file, or manni meta won't recognize it. Whichever flavor or
format is used, manni meta reads only the frontmatter, never the body, and
normalizes it to the same [metadata](#metadata) shape it validates. See
[Supported formats](/manni/meta/reference/formats/#frontmatter-flavors) for the
fence flavors and where each format keeps its frontmatter.

## metadata

The key/value pairs manni meta validates: `type`, `title`, `timestamp`, and so on.
Metadata is what an [extractor](#extractor) pulls out of a document's
[frontmatter](#frontmatter). Everything in manni meta after extraction operates on
this generic key/value shape, regardless of the original format. manni meta checks
the **presence and format** of metadata, never the document's prose.

## extractor

The format-specific component that reads metadata out of a document. manni meta has
one extractor per input format: Markdown, MDX, AsciiDoc, reStructuredText, XML,
and HTML. The extractor is the only part of manni meta that knows about a file's
format. Once it produces metadata, validation and reporting work the same for
every format. You can force a specific extractor with `--as`, which is required
when reading from stdin. See [Supported formats](/manni/meta/reference/formats/).

## schema

A [JSON Schema](https://json-schema.org/) document that declares which metadata
fields are required, which are optional, and what shape each value must take.
manni meta validates a file's metadata against one or more schemas. A schema can be
shipped with manni meta (a [builtin](#schema-reference)), a local file, or a remote
URL.

## schema set

The one-or-more schemas resolved for a single file. manni meta resolves a schema
**set** per file, then validates the file's metadata against **every** schema in
it. A file passes only when it satisfies all schemas in its set, and each
reported error is tagged with the schema that produced it. See
[Schema resolution](/manni/meta/reference/schema-resolution/#validating-against-the-whole-set).

## schema reference

A pointer to a schema, meaning what appears in a `--schema` flag, a document's
[`$schema`](#schema-document-key) key, or config. manni meta classifies each
reference into one of three kinds by its shape:

- **builtin**: a `vendor:name:version` id such as `google:okf:0.1`, resolved to
  a schema shipped with manni meta.
- **file**: a `.json` path or any path with a separator, such as
  `./my.schema.json`, resolved from the local filesystem.
- **url**: an `http://` or `https://` URL, fetched over the network.

See [Reference kinds](/manni/meta/reference/schema-resolution/#reference-kinds).

## `$schema` (document key)

A reserved key a document can put in its own metadata, to name the schema or
schemas it should be validated against. It takes a single reference or a list.
Because it's a manni meta directive rather than real metadata, `$schema` is
**stripped before validation**, so a schema with `additionalProperties: false`
won't flag it. In the [precedence chain](#override) it sits above config but
below a `--schema` flag. See [The `$schema` key in a
file](/manni/meta/reference/schema-resolution/#the-schema-key-in-a-file).

## `$schema` (meta-schema URI)

A different use of the same key, found **inside a schema** rather than a document.
There, `$schema` is the meta-schema URI that declares the schema's
[dialect](#dialect), for example
`https://json-schema.org/draft/2020-12/schema`. manni meta reads it to decide which
validator to compile the schema with. Don't confuse it with the document
[`$schema`](#schema-document-key) above: one selects a dialect, the other selects
which schema validates a document.

## dialect

A version of the JSON Schema specification: Draft 2020-12, 2019-09, draft-07,
draft-06, or draft-04. manni meta auto-detects a schema's dialect from its
[`$schema` meta-schema URI](#schema-meta-schema-uri), and compiles it with the
matching validator. A missing or unrecognized URI falls back to Draft 2020-12.
Schemas of different dialects can coexist in one run. See
[Dialects](/manni/meta/reference/schema-resolution/#dialects).

## JSON Pointer

The standard ([RFC 6901](https://datatracker.ietf.org/doc/html/rfc6901)) syntax
manni meta uses to name the field an error is about. A pointer like `/tags/0` means
"the first item of the `tags` array". An empty pointer, shown as `(root)` in
pretty output, means the document as a whole. That is most often a required
field that's missing entirely. Pointers appear in error output and in the
`instancePath` field of JSON output.

## OKF

The Open Knowledge Format, whose v0.1 schema (`google:okf:0.1`) ships with
manni meta as the built-in default. OKF requires only `type` and treats every other
field (`title`, `description`, `resource`, `tags`, `timestamp`) as recommended,
tolerating unknown keys. It's what validates your files when nothing else is
configured. See [the built-in OKF schema](/manni/meta/reference/okf-schema/).

## override

In manni meta, "override" has two related senses:

- A config **`overrides`** entry assigns a schema set to files matching a glob, so
  different folders can use different schemas. See
  [Apply different schemas to different folders](/manni/meta/set-up/different-schemas-per-folder/).
- More broadly, schema resolution is a chain of overrides. A `--schema` flag
  overrides a document's [`$schema`](#schema-document-key). That overrides
  config `overrides`, which overrides config `schemas`, which overrides the
  built-in default. The first source that yields a schema wins. See
  [Precedence](/manni/meta/reference/schema-resolution/#precedence).

## validation vs. extraction

Two distinct operations, exposed as two commands. **Extraction** reads metadata
out of a document. The `get` command prints named field values and validates
nothing. **Validation** checks that extracted metadata satisfies its
[schema set](#schema-set). That is the `validate` command, the one CI gates on. Every
validation begins with an extraction, but you can extract without validating. See
the [CLI reference](/manni/meta/reference/cli/).
