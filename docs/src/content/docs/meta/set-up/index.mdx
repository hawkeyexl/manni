You own a docs repo, and you want every page to carry correct, complete frontmatter so search and your content catalog stay trustworthy. This guide threads the whole setup together. Install manni meta, validate a folder by hand, then capture your rules in a `manni.config.yaml`. Then land a CI gate that runs the same check on every pull request.

By the end you will have a committed config file and a check that fails the build when a doc is missing required metadata.

<Aside type="note" title="What manni meta checks">
manni meta validates the **presence and format** of your frontmatter against [JSON Schema](https://json-schema.org/): that `type` exists, that `timestamp` is a real date-time, that `resource` is a URI. It does not review your prose. If a field is required by your schema and missing, the run fails.
</Aside>

## Before you start

- **Node.js 24 or newer.** Check with `node --version`.
- A docs repo with frontmatter you want to enforce. The examples below assume Markdown under a `docs/` folder, but manni meta handles other formats too; see the [supported formats reference](/manni/meta/reference/).

## Stand it up

<Steps>

1. **Validate a folder, no setup required.**

   Run manni meta against a directory with `npx`. No install, no config. This tells you where you stand today.

   ```bash
   npx @hawkeyexl/manni meta validate docs/
   ```

   manni meta walks `docs/`, finds every supported file, and validates each one against the built-in [`google:okf:0.1`](/manni/meta/schemas/) schema, which requires a `type` field. You will see a pass/fail line per file and a summary. A nonzero exit code means at least one file failed.

   <Aside type="tip">
   To check a single file instead, pass its path: `npx @hawkeyexl/manni meta validate docs/intro.md`. Explicit file arguments are always validated, regardless of extension filters.
   </Aside>

2. **Add a `manni.config.yaml` at your repo root.**

   The command above works, but you do not want to retype paths and schemas every run. CI also needs a stored definition of what "valid" means for your repo. Capture it in a config file so a bare `manni meta validate` knows what to do.

   ```yaml title="manni.config.yaml"
   meta:
     # Default targets when no paths are passed on the command line.
     paths:
       - "docs/**/*.md"

     # The schema set every matched file must satisfy.
     schemas:
       - google:okf:0.1
   ```

   `paths` is the fallback manni meta uses when you do not name files on the command line. `schemas` is the set each file is validated against; every file must satisfy every schema you list.

   <LinkCard
     title="Create your manni.config.yaml"
     href="/manni/meta/set-up/config/"
     description="Every config key explained: paths, exclude, schemas, and overrides, with a complete worked example."
   />

3. **Run the stored configuration.**

   With the config committed, you no longer pass paths or schemas. manni meta discovers `manni.config.yaml` in the current directory and uses its `paths` and `schemas`.

   ```bash
   npx @hawkeyexl/manni meta validate
   ```

   This is the exact command CI will run. Confirm it reports what you expect locally before you wire it up.

   <Aside type="caution">
   If you run a bare `manni meta validate` with no config file and no paths, manni meta exits with code `2`. The message is `No files to validate.` That is an operational error rather than a silent pass. It means manni meta had nothing to do.
   </Aside>

4. **Land the CI gate.**

   The same `npx @hawkeyexl/manni meta validate` command becomes a pull-request gate. manni meta exits `0` when everything passes and `1` when a file fails validation, so any CI system can use it as a pass/fail step. The `--format github` flag turns failures into inline annotations on the PR diff.

   ```bash
   npx -y @hawkeyexl/manni meta validate --format github
   ```

   The full recipe (workflow file, exit-code contract, and annotation behavior) lives in the CI track. Copy the ready-made recipe there instead of assembling your own.

   <LinkCard
     title="Run it in CI"

   />

</Steps>

## What you have now

A committed `manni.config.yaml` that defines which files to check, and which schema they must satisfy. Plus a CI step that runs the same check on every pull request, and fails the build on bad metadata. New contributors get the same enforcement you do, without any review fatigue on your side.
