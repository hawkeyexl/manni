A schema is only useful once manni meta knows *which* schema applies to *which* file. In a real repo, several signals compete to answer that question. A flag on the command line and a `$schema` key inside the document both have a claim. So do a directory rule in your config and a repo-wide default. manni meta settles the competition with a fixed precedence order, and once you know that order, wiring schemas to documents becomes predictable instead of mysterious.

This page documents the precedence chain and the three kinds of schema reference you can use anywhere a schema is named. It also covers how manni meta detects a schema's JSON Schema dialect.

## The precedence chain

{/* cite first-source-that-yields-a-schema-wins */}
For every file, manni meta builds a **schema set** (the list of schemas that file will be validated against) by checking five sources in order. The **first source that yields a schema wins**, and the search stops there. Nothing lower in the list is consulted.

<Steps>

1. **CLI `-s`/`--schema`**: if you pass one or more `--schema` flags, they apply to *every* file in the run and override everything else. Repeatable; the flags together form the set.

2. **The file's own `$schema` key**: a `$schema` field in the document's metadata. May be a single string or a list of strings.

3. **The first matching `overrides` entry in config**: config `overrides` are checked in order; the first whose glob or collection matches the file supplies the set. Its schemas replace everything below, unless the entry sets `defaults: true`, which puts the default set first.

4. **Config `schemas`**: the repo-wide list in `manni.config.yaml`. It joins the default set, after it. `meta.defaults: false` makes it replace the defaults instead.

5. **The default set** applies when there are no config `schemas`. Its eleven built-ins are `google:okf:0.1`, `passo-uno:seven-action:1.0` and nine manni vocabularies, led by `manni:core:1.0.0`. Core requires `title` and `description`, so every file the defaults judge needs both.

</Steps>

<Aside type="note" title="The first level decides">
Each level is a full stop. If you pass `--schema`, the file's `$schema` key and all config rules are ignored for that run. If a file has a `$schema` key, config `overrides` and `schemas` are skipped. A level can add only the default set, at levels 3 and 4, and the strict versions `strict: true` stacks. To combine other schemas, list them at a *single* level: several `--schema` flags, a list-valued `$schema`, or multiple entries in one config rule. See [Validating against more than one schema](#validating-against-more-than-one-schema).
</Aside>

Here is the same chain as a quick-reference table:

| Order | Source | Scope | Notes |
|------:|--------|-------|-------|
| 1 | CLI `-s`/`--schema` | All files in the run | Repeatable; replaces everything below. |
| 2 | File `$schema` key | That one file | String or list of strings. A reserved key, stripped before validation. |
| 3 | Config `overrides` | Files matching a glob or a collection | First matching entry wins. Replaces, unless the entry sets `defaults: true`. |
| 4 | Config `schemas` | All files no override matched | The default set, then these. `meta.defaults: false` drops the defaults. |
| 5 | The default set | All files (last resort) | Eleven built-ins. See [the default set](/manni/meta/reference/schema-resolution/#the-default-set). |

At levels 3 to 5, `strict: true` stacks each strict version right after its base. That covers each `manni:` default and each [registered](#register-your-own-ids) schema that has one.

Levels 3 and 4 come from your `manni.config.yaml`. Here is the config the worked example below assumes, with a repo-wide house schema plus one directory override:

```yaml title="manni.config.yaml"
meta:
  # Level 4: the default set, then the house schema, for every file...
  schemas:
    - ./schemas/house.schema.json

  # Level 3: ...unless a file matches an override glob, checked top to bottom.
  overrides:
    - files: "api/**"
      schemas:
        - ./schemas/api.schema.json
```

{/* cite override-names-files-or-a-collection */}
Each `overrides` entry pairs a `schemas` list with the files it governs. The
files are named in **one** of two ways. A `files` glob, as above, names them by
pattern. `collection: <name>` names the members of a declared
[collection](/manni/meta/reference/configuration/#collections).
An entry carries exactly one of the two. Entries are tried in order, and the
first that matches the file supplies the set, whichever way it names its files.

Reach for `collection:` when the set is a real document set the repository
already declares, so the globs are written once. Keep `files:` for a glob that
only affects which schema applies. (For every config key, type, and default, see
the [Configuration reference](/manni/meta/reference/configuration/).)

<Aside type="tip" title="A worked example">
With the config above, a repo-wide house schema (level 4) and an override applying `api.schema.json` to `api/**` (level 3), resolution plays out like this:

- `api/auth.md` with no `$schema` key → matches the override → validated against **`api.schema.json`** alone. Add `defaults: true` to the entry to put the default set first.
- `guides/intro.md` with no `$schema` key → no override matches → falls through to level 4 → validated against **the default set, then `house.schema.json`**.
- Any file with `$schema: ./special.schema.json` in its frontmatter → the file key (level 2) beats both config levels → validated against **`./special.schema.json`**.
- The whole run invoked with `--schema ./audit.schema.json` → level 1 overrides all of the above → *every* file validated against **`./audit.schema.json`**.
</Aside>

## The `$schema` key is reserved

{/* cite strips-schema-before-the-validator */}
When a document names its own schema with a `$schema` key, that key is a *directive to manni meta*, not part of the document's metadata. manni meta strips `$schema` out of the metadata before handing it to the validator.

This matters for one specific case. A schema with `"additionalProperties": false` rejects any field it doesn't declare. Without special handling, a document carrying `$schema:` would fail against such a schema, because `$schema` isn't one of the schema's declared properties. Because manni meta removes `$schema` first, that never happens. You never need to add `$schema` to your schema's `properties`, and a self-describing document validates cleanly against even the strictest schema.

The `$schema` value can be a single reference or a list:

<Tabs>
<TabItem label="Single schema">

```markdown
---
$schema: ./schemas/metadata.schema.json
type: guide
title: My page
---
```

</TabItem>
<TabItem label="Multiple schemas">

```markdown
---
$schema:
  - google:okf:0.1
  - ./schemas/house-style.schema.json
type: guide
title: My page
---
```

The file is validated against *both* schemas; see [below](#validating-against-more-than-one-schema).

</TabItem>
</Tabs>

<Aside type="caution" title="$schema must be a string or a list of strings">
A `$schema` value that is anything else is a configuration error, and manni meta reports it rather than guessing. That covers a number, an object, and a list with non-string entries. Keep it to a single reference or a flat list of references.
</Aside>

Level 2 beating config is what makes a document self-describing, and it is also the one level a repository can narrow. A repo taking pull requests from outside can narrow it with [`schemaTrust`](/manni/meta/reference/configuration/#schema-trust). It can say that documents may name a built-in id or a repository file but not a URL. It can also ignore their `$schema` entirely. Left unset, level 2 behaves exactly as described here.

## The three reference kinds

Everywhere a schema is named, the value is a **reference**. That covers a `--schema` flag, a `$schema` key, and a config entry. manni meta classifies each reference into one of three kinds by its shape. You don't declare the kind; manni meta infers it.

<CardGrid>
  <Card title="Built-in" icon="seti:json">
  A `vendor:name:version` id with no path separators and not ending in `.json`.

  Example: `google:okf:0.1`

  Resolved from the schemas bundled into manni meta, or from a schema your config [registers](#register-your-own-ids) under that id. A typo'd id (e.g. an unknown vendor) is reported as an unknown schema, not silently treated as a missing file.
  </Card>
  <Card title="File" icon="document">
  A path that ends in `.json` **or** contains a path separator (`/` or `\`).

  Examples: `./schemas/api.schema.json`, `schemas/house.json`

  Read from the local filesystem. Relative paths resolve against the current working directory.
  </Card>
  <Card title="URL" icon="external">
  Anything starting with `http://` or `https://`.

  Example: `https://example.com/schemas/okf-1.0.json`

  Fetched over the network with a **10-second timeout** and **cached for the run**. The same URL is downloaded only once, even across thousands of files.
  </Card>
</CardGrid>

<Aside type="note" title="How the kind is decided">
The classification is purely structural, and it is applied in this order. A value starting with `http(s)://` is a **URL**. Otherwise a value with no slash or backslash, not ending in `.json`, and shaped like `vendor:name:version` is a **built-in**. Everything else is a **file**. That last rule is why a Windows path like `C:\schemas\my.schema.json` is correctly treated as a file rather than mistaken for a built-in id.
</Aside>

<Aside type="caution" title="A schema that can't be loaded is a hard error">
If a reference can't be resolved, manni meta stops with an operational error (exit code 2). It does not skip the file or fall back to the default. This applies to an unknown built-in id, a missing schema file, and a URL that 404s or times out after the 10-second limit. Treat the schema reference as load-bearing: a broken one fails the run, which is what you want in CI.
</Aside>

### Register your own ids

A house schema is a file, so every config entry names it by path. [`meta.register`](/manni/meta/reference/configuration/#register) gives it an id instead. The config lists the file or its directory, and the schema's own `$id` becomes a name like `house:page:1.0.0`. That id then works in config, on `--schema`, in a document's `$schema`, and in a `$ref` from another schema, exactly as a built-in id does. [Name your schema and its strict version](/manni/meta/schemas/#name-your-schema-and-its-strict-version) walks through it.

URL references are one way to govern a single schema across many repos: a central, versioned schema URL that every consumer points at. Vendoring that URL into each consumer is the other, and the more durable one. Both, with the fetch timeout and caching behavior in depth, are covered in [Govern a shared schema across repos](/manni/meta/ci/govern-shared-schema/).

## Validating against more than one schema

{/* cite every-schema-in-the-set-is-applied */}
When a file's schema set contains more than one reference, manni meta validates the file against **every schema in the set**. It reports the union of all violations, each tagged with the schema that produced it. A file passes only if it satisfies all of them.

A multi-schema set is what you get when you name several schemas at a single precedence level:

- several `--schema` flags on the command line,
- a list-valued `$schema` key in a document,
- or multiple entries in one config `overrides` rule or in config `schemas`, which the default set joins.

This is useful for layering a shared organizational schema with a local one. For example, validate against a company-wide `house-style.schema.json` *and* a team-specific `api.schema.json` at once. Each schema is compiled and cached separately, so layering is cheap.

Because the file must satisfy *every* schema in the set, the strictest member governs. If any schema in the set sets `"additionalProperties": false`, an unknown key fails the file even when another schema in the set allows it. Keep that in mind when combining a lenient shared schema with a strict local one; the strict one wins on every rule it imposes.

## Dialects are detected automatically

{/* cite dialect-read-from-the-schema-line */}
JSON Schema has evolved through several versions, called *dialects* (draft-04, draft-06, draft-07, 2019-09, 2020-12). A schema written for one dialect can fail to compile under another. So manni meta reads each schema's **own `$schema` line** and selects the matching validation engine. That line is the URI at the top of the schema file. It points at the dialect's *meta-schema*, the schema that defines the dialect itself.

manni meta supports these dialects:

| Dialect | Detected from a `$schema` URI containing |
|---------|------------------------------------------|
| 2020-12 | `2020-12` (also the fallback) |
| 2019-09 | `2019-09` |
| draft-07 | `draft-07` or `draft/7` |
| draft-06 | `draft-06` or `draft/6` (shares the draft-07 engine) |
| draft-04 | `draft-04` or `draft/4` |

If a schema omits its `$schema` line or uses an unrecognized one, manni meta falls back to **2020-12**, the dialect of the built-in schemas. Because of that auto-detection, a schema you fetch from a remote URL can target draft-07. It still validates correctly alongside a local 2020-12 schema in the same run.

<Aside type="tip" title="Always declare your dialect">
Relying on the fallback works, but stating the dialect explicitly removes ambiguity for both manni meta and the humans reading your schema. Keep a `"$schema"` line at the top of every schema file:

```json
{ "$schema": "https://json-schema.org/draft/2020-12/schema", ... }
```
</Aside>

For the full lookup table of precedence, reference kinds, and dialects in one place, see the [Schema resolution reference](/manni/meta/reference/schema-resolution/).
