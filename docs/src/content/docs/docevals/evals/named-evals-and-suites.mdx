The gate worked on one page, so it got copied. Now the same assertion exists in twelve pages with
three slightly different wordings. Nobody can say what a how-to page is actually checked for.

This is where manni docevals stops being a linter and becomes a standard.

## Name the eval once

Move it into `manni.config.yaml` under `evals`:

```yaml
docevals:
  evals:
    no-future-promises:
      type: regression
      assertion: The page makes no claims about unreleased or future functionality.
      grader: ai
      evidence: All prose sections
      examples:
        pass: Describes only shipped behavior.
        fail: Says "coming soon" or references an unreleased version.
```

Pages reference it by name:

```yaml
evals:
  - use: no-future-promises
```

Change the wording in one place and every page that uses it changes. Names match
`^[a-z0-9][a-z0-9-]*$`.

## Group them into suites

A suite is a named group plus a target pass rate, the checks that apply to a *kind* of page.

```yaml
docevals:
  suites:
    reference:
      target-pass-rate: 1.0
      evals: [no-future-promises, names-an-action, no-todo-markers]
    tutorial:
      target-pass-rate: 0.7
      evals: [explains-why-before-how, no-future-promises]
    how-to:
      target-pass-rate: 1.0
      evals: [no-future-promises, no-todo-markers]
```

```yaml
---
title: Installation
eval-suite: how-to
---
```

Set `defaults.suite` to apply one to every page that names none, and pages only carry an `evals` key
when they need something specific.

## `target-pass-rate` is a suite property

This is the piece people miss.

Individual verdicts are binary. The nuance lives in the **rate across a suite**:

- **1.0** for a regression suite. These checks must all hold.
- **~0.7** for a capability suite. This measures how far a quality goal has spread, and a corpus
  partway there is the expected state. Its failing evals still exit `1`, so it runs outside the
  merge gate.

```console
Suites
  reference: 1/2 passed — 0% vs target 100% below target (1 skipped)
```

A suite below target fails the run, and so does every failing eval in it, whatever the target. A
target below 1.0 changes the suite's verdict, not the exit code. To keep a capability suite from
blocking merges, run it outside the merge gate. See
[Regression vs capability](/manni/docevals/evals/regression-vs-capability/).

Skipped evals are excluded from the rate entirely, and so are evals awaiting human review. The
rate is computed over the **graded** set, which is pass, fail, and error. The rate is weighted and
the count is not, which is why `1/2` above reads `0%`. Both graded evals belong to one failing
criterion, scored once. Weights and criteria come next.

### Not every eval has to count the same

By default each eval contributes 1. `weight` changes how much an outcome moves the rate, and
nothing else. The eval still passes or fails on its own terms, and the counts stay counts.

```yaml
docevals:
  evals:
    names-an-action:
      assertion: The page documents at least one Doc Detective action.
      grader: tool:regex
      options:
        pattern: "(goTo|find|click|checkLink|httpRequest)"
      severity: warning
      weight: 0.5      # secondary: it reports, it does not dominate
```

Zero is rejected. A weightless eval is a silent disable, and `eval-skip` already means that,
loudly.

### Several evals scored as one

Sometimes two checks only mean something together. A `criterion` groups them and scores the group
**once**, so writing three checks as a group cannot outvote three standalone evals:

```yaml
docevals:
  criteria:
    action-page-is-trustworthy:
      evals: [names-an-action, no-todo-markers]
      combine: all      # or `any`
      weight: 2
  suites:
    reference:
      evals: [no-future-promises, names-an-action, no-todo-markers]
      criteria: [action-page-is-trustworthy]
```

Members keep their own results, so a report still says which one failed. A criterion whose members
were not all graded, through a filtered run or a skipped member, is **suspended** rather than failed.
A group measured in part has numbers but no verdict.

## Run one suite

`--suite <name>` narrows `run` and `list` to the evals that report under a suite:

```bash
npx @hawkeyexl/manni docevals list --suite reference
npx @hawkeyexl/manni docevals run --suite reference --deterministic-only
```

It selects the evals that **report under** that suite. That is the same suite you see in `list`
output and in the summary. A page gets it from its own `eval-suite` or from `defaults.suite`. So `--suite
reference` runs everything on the reference pages and nothing on a `how-to` page, even where the two
suites are composed of overlapping evals.

Two things it does *not* do. It does not redefine anything: `target-pass-rate` is untouched, and a
page still reports under its own suite. And it does not measure a target. The run saw only part of
the corpus, so the summary comes back `partial`, printing its numbers and withholding the verdict:

```console
Suites
  reference: 9/10 passed — 79% vs target 100% partial — filtered run, target not evaluated (6 skipped)
```

That run still exits `1`, because one of the ten genuinely failed. Suspending the *target* does
not suspend the findings. A filtered run stops claiming that the suite as a whole is in good
standing. It does not stop reporting that something it looked at was wrong.

Naming a suite the config does not define is exit 2, with the defined names in the message. Full
behavior, including the per-eval `--eval` filter, in
[Selecting evals suspends suite enforcement](/manni/docevals/reference/cli/#selecting-evals-suspends-suite-enforcement).

## Attach evals by doctype

A suite per page type repeats a routing that already exists. `manni lint` sends
every `type: how-to` page to a how-to template, and an `eval-suite: how-to` on
each page says the same thing again. Nothing checks that the two agree. A page
that changes to `type: reference` keeps its how-to suite in silence.

A lint template can carry the evals itself, under its own `evals` key.
`manni docevals` grades them on every page lint routes to that template, and
the page carries no key for it:

```yaml title="templates.yaml"
templates:
  how-to:
    types: [how-to]
    extends: tgdp:how-to:1.6
    evals:
      - use: no-future-promises
      - id: shows-the-command
        assertion: The page shows the command it is about.
        grader: tool:regex
        options: { pattern: "manni [a-z]+", match: contains }
```

Register the file under `lint.templates` in `manni.config.yaml`, and every
how-to is graded on both. A `use:` entry names an eval from your
`docevals.evals` library, so the assertion still lives once. The
[templates reference](/manni/lint/reference/templates/#evals) has the entry
forms, the `extends` merge and what a template cannot carry.

### Typed pages already get the built-in evals

The built-in templates carry The Good Docs Project's guidance for each doctype
as `tgdp-*` evals. A page whose `type:` is a built-in doctype gets them with no
config at all:

```console
$ manni docevals list docs/rotate-key.md
docs/rotate-key.md (template: tgdp:how-to:1.6)
  - tgdp-overview-names-the-task [ai, regression, template]
      The overview says which task the guide covers and when or why a reader would want to do it.
  - tgdp-steps-start-with-a-verb [ai, regression, template]
      Each numbered step tells the reader what to do with an imperative verb, optionally after a short lead-in such as "To do X,".
  - tgdp-one-action-per-step [ai, regression, template]
      Each numbered step asks the reader to do one thing, with any further actions given as separate steps or substeps.
  - tgdp-shows-the-result [ai, regression, template]
      Where the page has the reader run commands, it shows what successful output or a successful result looks like.
  - tgdp-no-concept-teaching [ai, regression, template]
      The page does not stop to teach concepts; background longer than a sentence or two is linked to another page instead.
  - tgdp-one-method [ai, regression, template]
      The page documents one recommended way to complete the task and mentions other methods only briefly or by link.

1 pages, 6 evals resolved
```

Each one is an `ai` regression at `error` severity, so a judged run fails on
it. `--deterministic-only` skips them, as it skips every `ai` eval, so a CI
gate that runs deterministic evals alone is unchanged. To turn one off for the
repository, extend the built-in and narrow it with `use: <id>` and
`skip: true`. For one page, put that same entry in the page's `evals`. The
[templates reference](/manni/lint/reference/templates/#the-built-in-evals)
lists every built-in eval.

### Which to reach for

| You want | Use |
|---|---|
| A check that follows the doctype, wherever lint routes the page | Template `evals` |
| The doctype's built-in guidance, adapted to your house | A template that `extends` the built-in |
| A target pass rate, criteria or weights over a group of evals | A suite |
| A group that cuts across doctypes, or one `--suite` can select | A suite |

The two compose. A page's suite evals come first, then its template's, then its
own entries. A template's inline entry replaces a suite eval with the same id,
and a page entry wins over both. The
[resolution order](/manni/docevals/reference/frontmatter/#resolution-order)
spells it out.

## Referential integrity is checked at load

Two mistakes fail immediately with exit 2 rather than surfacing later as a confusing per-page
problem:

- A suite referencing an eval that is not defined.
- `defaults.suite` naming a suite that does not exist.
- A template `use:` entry that neither a template it extends nor `docevals.evals` defines.

## Narrow without forking

When one page needs a variant, override at the reference rather than defining a near-duplicate:

```yaml
evals:
  - use: no-todo-markers
    severity: warning
```

`options` merges over the base; `type`, `severity`, and `skip` replace. A second eval with the id
`no-todo-markers-but-softer` is how a library rots.

## Check what resolved

Suites, templates, references, and inline definitions can all contribute the same name, and **page
entries win on collision**. Do not guess:

```bash
npx @hawkeyexl/manni docevals list docs/actions/find.mdx
```

```console
docs/actions/find.mdx (suite: reference)
  - no-future-promises [ai, regression, config]
      The page makes no claims about unreleased or future functionality.
  - names-an-action [tool:regex, regression, config]
      The page documents at least one Doc Detective action.
  - no-todo-markers [tool:regex, regression, config]
      The page carries no TODO, TBD or FIXME markers.
  - has-examples-heading [command, regression, page]
      The page includes an Examples heading.

1 pages, 4 evals resolved
```

`source`, the third item, is `config`, `template` or `page`, which is exactly what you need when one
page behaves unlike its neighbours. A page lint routes to a template names it in its header, as
