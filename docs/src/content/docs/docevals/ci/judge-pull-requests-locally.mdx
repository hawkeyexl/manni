This site's own docs run exactly this workflow, as
[`docs-judge.yml`](https://github.com/hawkeyexl/manni/blob/main/.github/workflows/docs-judge.yml).
It judges the ai evals on the pages a pull request changed. The model runs on the CI runner, so
the job needs no secret and sends no page text anywhere.

The judge reads its provider and model from your config. Name both, so every runner judges with
the same model:

```yaml
docevals:
  provider: llama-cpp
  model: granite-4.1-3b-q2
  judge:
    ensembleRuns: 3
    concurrency: 1
```

## The workflow

```yaml
name: Docs judge

# Judges the ai evals on the pages a pull request changed, with the local
# model the root manni.config.yaml names: llama-cpp, granite-4.1-3b-q2, three
# runs per eval. A page counts as changed when its file or the manifest that
# carries its evals changed. A judged fail fails the job; needs-review passes.
# docs/src/content/docs/docevals/ci/judge-pull-requests-locally.mdx documents
# this workflow and cites its lines, so `manni cite check` notices when the
# two drift apart.
on:
  pull_request:
    paths:
      - "docs/src/content/docs/**"
      - "manni.config.yaml"
      - ".github/workflows/docs-judge.yml"

permissions:
  contents: read

# One judge per pull request. A newer push cancels the run in progress. The
# verdicts that run finished are saved below, so the new run reuses them.
concurrency:
  group: docs-judge-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  judge:
    runs-on: ubuntu-latest
    # Above the turn budget below, so a large pull request ends on the budget
    # rather than on the runner's limit.
    timeout-minutes: 180
    steps:
      - uses: actions/checkout@v7
        with:
          # --since diffs against the base branch, which needs its history.
          fetch-depth: 0
      - uses: actions/setup-node@v6
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm run build
      # The node-llama-cpp runtime and the weights, about 2.1 GB. Same key as
      # docs-as-tests, which names the same alias.
      - uses: actions/cache@v4
        with:
          path: ~/.hawkeyexl-inference
          key: inference-local-granite-4.1-3b-q2-${{ runner.os }}
      # Verdicts this pull request's earlier runs finished. The cache is keyed
      # on the page text and the eval, so only what changed is judged again.
      - uses: actions/cache/restore@v4
        with:
          path: .manni/docevals/cache
          key: docs-judge-${{ github.event.pull_request.number }}-${{ github.run_id }}
          restore-keys: docs-judge-${{ github.event.pull_request.number }}-
      # --ai-only: a model that cannot start is exit 2, not a quiet
      # deterministic pass. ci.yml and docs.yml run the deterministic evals.
      # --max-turns: about 80 evals at three runs. Past it, the rest are
      # skipped and reported, and the next push continues from the cache.
      - name: Judge the changed pages
        run: >-
          node dist/cli.js docevals run --ai-only
          --since origin/${{ github.base_ref }}
          --max-turns 240 --format github
      # Saved on success, failure and cancellation alike, so a run replaced
      # by a newer push keeps the verdicts it reached.
      - name: Save the verdicts
        if: always()
        uses: actions/cache/save@v4
        with:
          path: .manni/docevals/cache
          key: docs-judge-${{ github.event.pull_request.number }}-${{ github.run_id }}
```

This repository builds manni from source, so it runs `node dist/cli.js`. In your repository,
replace the build step and that path with `npx @hawkeyexl/manni`. Change the `paths:` globs to
where your pages and manifests live.

`--ai-only` keeps the job to judged evals. A model that cannot start then exits `2` instead of
passing on the deterministic evals alone. Run those in a separate job with `--deterministic-only`,
as [Run it in CI](/manni/docevals/ci/) shows.

## One judge per pull request

A judged run takes minutes, and contributors push while it runs. The `concurrency` group is keyed
on the pull request number, with `cancel-in-progress: true`. A newer push to the same pull request
cancels the run in progress and starts again on the new commit. Different pull requests still
judge in parallel.

Cancelling would throw work away, except that the verdict cache is saved with `if: always()`. That
step runs on success, on failure and on cancellation. The replacing run restores the cache through
`restore-keys` and re-judges only what changed since, or what the cancelled run never reached.

The cache is content-addressed. Its key covers the page text, the eval, the provider, the model
and the number of runs. A verdict for an unchanged page therefore stays valid on the new commit.
See [Caching and turn budgets](/manni/docevals/ci/cost-and-caching/) for everything the key
covers.

## Only what changed

`--since origin/<base>` grades only the pages that differ from the branch the pull request targets.
A page differs when its own file changed. It also differs when a manifest that supplies its
`evals`, `eval-suite` or `eval-skip` changed. An edit to one assertion in a `.meta.yaml` sidecar
therefore judges the page it belongs to.

The diff runs against the merge base, so the checkout needs `fetch-depth: 0`. A pull request that
changes no page judges nothing and exits `0`. The
[CLI reference](/manni/docevals/reference/cli/#scoping-a-run-to-what-changed) has the full rule.

## What it costs on a hosted runner

These times were measured on a GitHub-hosted `ubuntu-latest` runner, with 4 vCPUs and 15 GB of
memory. The judge was `granite-4.1-3b-q2` with three runs per eval and no verdict cache:

| Page size | Evals | Time to judge |
|---|---|---|
| 1.6 KB | 1 | 138 s |
| 6.9 KB | 2 | 772 s |
| 14 KB, read in chunks | 2 | 706 s |

That is about 2 to 13 minutes per page. The same three pages took 775 s in total on a different
runner, so the runner's CPU swings the time by about two times. With the model cache warm,
fetching and loading the model adds about 20 to 45 seconds.

Two limits bound a large pull request. `--max-turns 240` caps the judge at 240 model calls, which
is 80 evals at three runs each. Past the cap, the remaining evals are skipped and reported, the
run still exits `0`, and the next push continues from the cache. `timeout-minutes: 180` caps the
job's wall-clock time. At the rates above, 80 evals take longer than 180 minutes, so a pull
request that changes many judged pages meets the timeout first.

## Blocking, and the judge's consistency

The job uses docevals' own exit codes. A judged `fail` exits `1` and fails the check. A verdict
of `needs-review` passes with exit `0`. So does an errored run, because it lands in
`needs-review`. Whether a red check blocks the merge is your branch-protection setting.

A small quantized model is not always consistent. In the measurements above, the same eval on the
same text got different verdicts on different runs. Before you make the check required,
[calibrate the judge](/manni/docevals/judge/calibrate/) against a golden set. Then fix or reword
the evals whose verdicts change between runs.

## The model and runtime cache

The `node-llama-cpp` runtime and the model weights live in `~/.hawkeyexl-inference`, about 2.1 GB.
The first `actions/cache` step keeps them between runs, so only a cold cache downloads them.

The cache key must name the model alias your config pins, as `granite-4.1-3b-q2` does here. A new
alias then gets a new cache entry instead of a stale one. Change the key in the same commit that
changes `model:`.
