manni validates, queries and fills page metadata. It keeps terminology
consistent and tracks which sentences rest on which source lines. It builds a
knowledge graph of the docset and tests the procedures in it. It runs evals
over the pages and over the agent sessions that write them. Every check runs
the same way in CI, by hand, and in an agent session.

## Why check documentation

Documentation decays quietly. Code has tests, so a change that breaks it goes
red before it ships. A docs page has no such check. When it breaks, a reader
finds out first.

It breaks in a handful of familiar ways, and each manni tool catches one.

| What goes wrong | What catches it |
|---|---|
| A required field goes missing, and search, the site nav or a docs bot drops the page. | [`meta`](/manni/meta/) |
| A sentence describes code that has since changed. | [`cite`](/manni/cite/) |
| A procedure stops working when someone follows it. | [`test`](/manni/test/) |
| Two pages call one thing by different names, so search and translation split it. | [`term`](/manni/term/) |
| A how-to loses the steps a how-to needs. | [`lint`](/manni/lint/) |
| A page falls below the quality bar the team wrote down. | [`docevals`](/manni/docevals/) |
| A page nothing links to, or one concept spelled two ways. | [`graph`](/manni/graph/) |
| A page shuts out a reader who uses a screen reader or has low vision. | [`a11y`](/manni/a11y/) |
| An agent writing the docs stops following its instructions. | [`tracevals`](/manni/tracevals/) |
| A page claims a persona or journey nobody keeps a record of. | [`strategy`](/manni/strategy/) |

Each check fails on the pull request that caused the problem, with the file,
the line and the rule. A reviewer's eye stops being the only gate.

manni does not grade prose style. Linters such as Vale do that, and
`manni term` writes your glossary into a Vale style so the two agree on names.
manni checks what a page claims about itself, about the code it describes, and
about the other pages.

## Who it's for

- **You own a docs repository** and review is the only thing enforcing your
  standard. Start with [meta](/manni/meta/).
- **You run CI for many repositories** and want one gate that reads the same
  in each. Start with [manni check](/manni/family/check/).
- **You define what pages must carry** and need the standard to change
  without breaking every repo at once. Start with
  [Author a schema](/manni/meta/schemas/).
- **You generate or edit docs with an agent** and want deterministic checks to
  steer it. Start with [the Claude Code plugin](/manni/family/claude-code/).
- **Your pull request is red** and you did not set up the check. Each tool's
  section has a *Fix a failing check* page, such as
  [the one for meta](/manni/meta/fix/).

## How the tools fit together

`meta` checks what a page says about itself. `lint` checks whether it is shaped
like what it says it is. `cite` checks that what a page says about the code is
still true. `docevals` checks that a page still meets the quality bar its team
wrote down. `tracevals` checks that an agent session followed the instructions
it ran on. `term` checks that the terms a page names are defined, and carries
those terms into Vale and translation. `strategy` checks that the audiences,
personas and journeys a page names are ones the docset keeps records of. `graph` checks what the pages say about
each other, which is the only question no single file can answer. `key` sets and
rotates the one encryption key that `meta` and `cite` encrypt values with.
`test` checks that a procedure still works when someone follows it.
`site` runs the docs site itself, the one `a11y` crawls, through its
framework's own commands. `vector` builds a semantic index of the pages, keyed
by the same ids as the graph, so search and retrieval rank by meaning.
`manni --help` lists exactly the tools the package carries.

## Install and run

Almost every command reads `manni <domain> <subcommand> [<subcommand>] [<arguments>]`,
and the domain is the tool. The two exceptions run across the tools, and the
next section covers them. `manni meta validate docs/` runs the metadata
tool's `validate` against `docs/`, and `manni meta schemas vendor` reaches a
verb one level down. Each tool has its own commands, its own section of this
site, and its own key in one shared config file, `manni.config.yaml`. Install
the package once and every tool is there.

```sh
npm install -D @hawkeyexl/manni
npx @hawkeyexl/manni meta validate docs/
npx @hawkeyexl/manni docevals run docs/ --deterministic-only
```

## Everything a repository set up, in one command

`manni status` says which tools a repository set up. `manni check` runs every
check they carry, and skips the rest. It is the same command in CI, by hand,
and in an agent session. There, the manni plugin for Claude Code runs it after
each edit.

```sh
npx @hawkeyexl/manni status
npx @hawkeyexl/manni check
```

## Coming from docmeta?

The metadata tool used to be the whole package. Three things changed, and
nothing else did:

- **The command.** `docmeta validate …` is now `manni meta validate …`. The
  package still installs a `docmeta` bin that runs the same program, so
  existing scripts keep working while you move them.
- **The config file.** `manni.config.yaml`, with the metadata tool's keys under
  `meta:`. A `docmeta.config.yaml` is still read, with a warning. See
  [the configuration reference](/manni/meta/reference/configuration/#discovery).
- **The GitHub Action.** `uses: hawkeyexl/manni@v4` now runs `manni check`,
  every check the repository has set up. Add `command: meta validate` to run
  the metadata check alone, with the inputs it took before. See
  [the Action reference](/manni/family/reference/action/).

Every built-in schema keeps its old published URL as well as its new one, so a
`$schema` line written before the rename still resolves offline. See the
[built-in schema registry](/manni/meta/reference/schemas/).
