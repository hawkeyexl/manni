title: See which journeys readers actually take
description: Sara joins a page-views export to her strategy records and reads traffic per journey and per persona.
personas: [sara]
---

**Outcome.** Sara can say how many readers each journey and each persona drew, from one command over the records she already keeps. The traffic the strategy does not explain has a name. That is a much-read page that names no journey, or a URL that maps to no page.

**Steps.** Sara's trigger is a strategy review where S17 reports every page checked, and nobody can say whether readers take the journeys. She exports page views from her analytics tool as a JSON list of `page`, `views` and `exits`. She saves it under `.manni/`, which git ignores, so the numbers stay on her machine. She copies the route from `graph.routes` into the first line of `docs/content-strategy/traffic.sql`. She runs `manni meta query` with that file as `--query` and the export as `--param views:=<json>`. The result has one row per persona and per journey, with pages, measured pages, views and an exit rate. An `unplanned` row is a read page that names no journey. An `unmatched` row is a URL that maps to no page. She lists the journeys with pages and no views through `-f json`, and keeps a CSV for the quarterly review with `-f csv`.

**What success looks like.** The review starts from numbers, not from a claim. The home page that names no journey shows up as an `unplanned` row, and a renamed page shows up as an `unmatched` URL. The export never leaves Sara's machine, and no CI run needs it. The related journey is S17, which holds the pages to the same records.
